# 第 3 章 基因组组装

## 3.1 这一层要回答什么问题

组装表面上只做一件事：把读长拼成更长的序列。但真正决定成败的是三个互相牵连的问题，它们必须在动手前想清楚，因为**组装没有回头路**——后面所有步骤（注释、分型、比较）都建在这一步的产物上。

### 问题一：我手上这批读长是不是来自一个基因组？

这不是组装问题，而是组装的前提。混入第二个菌株、宿主 DNA 或试剂污染物时，组装器不会报错，反而可能给出**更好看**的结果：单条长 contig、没有碎片、N50 极高。原因很直接——来自两个近缘基因组的读长在重复图里能互相补全覆盖度，嵌合连接因此更容易通过阈值。

由此得到本章最重要的一条流程纪律：

> **污染筛查必须发生在组装之前。** 组装后才发现污染，代价是要重跑整条下游链路；组装前筛查的成本只是几分钟的 k-mer 分类。

两类筛查的分工要分清：读长层面的筛查（第 2 章 `qc_contamination_screen`）回答「这批数据里有什么」，组装产物层面的检验（第 4 章 `asmqc_checkm2`、`asmqc_gunc`）回答「这份基因组是否纯净」。前者便宜、早、定性；后者严格、晚、定量。**两者不能互相替代**，因为近缘污染（同种不同株）在读长层面和标记基因层面都可能看不出来。

### 问题二：我要的是草图，还是完成图？

这个问题决定了整个工具选择，而它不由「想要多好」决定，由下游问题决定。为了让判断可操作，需要先把「完成度」拆成三个互相独立的维度——它们经常被混为一谈：

| 维度 | 由什么衡量 | 与另两个维度的关系 |
|---|---|---|
| **连续性** | contig 数、N50、最长 contig（`asmqc_quast`） | 高连续性完全可能伴随内容缺失（例如把一段污染拼成了长 contig） |
| **基因内容完整性** | BUSCO 完整度、CheckM2 完整度（`asmqc_busco`、`asmqc_checkm2`） | 与连续性无关：一份 500 个 contig 的草图可以有 99% 的 BUSCO 完整度 |
| **结构正确性** | 读长回贴覆盖度是否在某处断裂、接触图、与近缘基因组的共线性 | **最容易被忽略**：N50 与 BUSCO 都对它不敏感 |

把这三个维度分开看之后，「需要什么完成度」这个问题才有答案：

| 下游问题 | 连续性 | 内容完整性 | 结构正确性 | 判断依据 |
|---|---|---|---|---|
| 物种鉴定（ANI、GTDB 分类） | 低要求 | 完整度 > 90% 即可 | 不要求 | 标记基因与全基因组比对对碎片不敏感，但对缺失内容敏感 |
| 耐药 / 毒力基因筛查 | 低要求 | 目标基因被完整拼出 | 不要求 | 基因级结论只依赖目标区域，contig 碎不影响 |
| cgMLST / SNP 分型 | 中要求 | 高 | 中 | 位点落在 contig 边界会被记为「未检出」，碎片化会系统性抬高菌株间距离 |
| 基因内容比较（泛基因组、存在/缺失） | 中要求 | 高 | 不要求 | 假家族主要来自注释不一致（第 7 章），但截断基因同样会制造假家族 |
| 质粒与复制子结构、接合转移 | **完成图** | 高 | **高** | 短读长无法区分「质粒」与「染色体上的复制子样序列」 |
| 染色体结构、倒位/易位、共线性 | **完成图或染色体级** | 高 | **高** | 草图的 contig 断点会被算法记成重排（第 7 章会展开这一点） |
| 提交 NCBI / 发表 | 通常草图即可 | 高 | 中 | 受污染的公开基因组代价极高，但完成度通常不是硬门槛 |

### 问题三：我的数据是什么读长类型？

短读长、长读长、两者都有，对应三条完全不同的路线，且不能互相替代（见 3.3）。有一件事需要提前说清楚：

> **混合组装不是「更好的默认选项」。** 它解决的是一个具体问题——用短读长修长读长的碱基错误、用长读长解短读长解不开的重复。如果只有短读长，Unicycler 相比直接用 SPAdes 没有实质优势，反而更慢、依赖更多。

### 这一层的产物到底是什么

组装的产物不是「更好的数据」，而是：

1. 一组序列；
2. 这些序列上**断点位置的完整清单**；
3. 以及对每个断点成因的解释（重复区？覆盖度不足？污染？reads 太短？）。

判断组装好坏的标准是「断点是否落在你关心的地方」，而不是 N50 的数字。长读长组装器的一个关键优势正在于它把第 3 项显式写了出来（Flye 的 `assembly_info.txt` 会标记 `repeat` 与 `circular`），而 de Bruijn 图组装器的断点通常只能靠读长回贴覆盖度去推断。

## 3.2 输入、输出与中间文件长什么样

### 输入

| 类型 | catalog 类型 id | 典型来源 | 关键要求 |
|---|---|---|---|
| 清理后双端读长 | `clean-reads` | `qc_fastp` / `qc_trimmomatic` | 接头已去、长度阈值一致；宏基因组不要做 PCR 去重 |
| 过滤后长读长 | `long-reads` | `qc_quality_trim_long` | 保留长尾；覆盖度按**碱基数**算而不是读长条数 |
| Hi-C 双端读长 | `hic-reads` | 建库测序 | 需先统计有效配对比例与覆盖度，否则挂载接近随机 |

### 输出与中间文件

组装阶段最容易出的问题不是数据错，而是**版本混用**：同一个样本会有三到五个「基因组文件」同时存在，名字都很像。

```
02_assembly/
├── sample_spades/
│   ├── contigs.fasta          # 不含 N，注释与提交用这个
│   ├── scaffolds.fasta        # 用 N 连接，N50 更好看，信息没变多
│   ├── assembly_graph.gfa     # 图结构；排查可疑连接时唯一的一手材料
│   ├── contigs.paths          # contig 在图上的路径（SPAdes）
│   └── spades.log             # 参数与 k 值列表都在这里
├── sample_skesa/
│   └── sample.skesa.fasta     # 建议显式命名，不要用默认文件名
├── sample_flye/
│   ├── assembly.fasta         # 组装序列
│   ├── assembly_info.txt      # 每个 contig 的长度/覆盖度/circular/repeat 标记
│   ├── assembly_graph.gfa
│   └── flye.log
├── sample_unicycler/
│   ├── assembly.fasta         # 最终组装（已含 Pilon 抛光）
│   └── assembly.gfa
├── sample.polished.fasta      # 抛光后（Medaka / Racon / Pilon / POLCA）
├── sample.filtered.fasta      # 长度过滤后，注释与提交用这个
└── sample_hic/
    └── yahs_out_scaffolds_final.agp   # 每个 scaffold 由哪些 contig、以什么方向组成
```

### 各工具的核心输出对照

| 工具 | 序列文件 | 最有诊断价值的附属文件 | 它回答什么 |
|---|---|---|---|
| SPAdes | `contigs.fasta` / `scaffolds.fasta` | `assembly_graph.gfa`、`spades.log`（k 列表） | contig 更长，但断点成因需要自己推断 |
| SKESA | 由 `--contigs_out` 指定 | 运行日志 | 序列更保守，contig 更碎 |
| Flye | `assembly.fasta` | `assembly_info.txt`（`length` / `cov` / `circular` / `repeat`） | **断点成因被显式记录**：哪些是重复区导致的 |
| Unicycler | `assembly.fasta` + `assembly.gfa` | 加 `--keep` 后的桥接中间文件 | 桥接依据是什么，可疑连接在哪 |
| YaHS / SALSA2 | `*_scaffolds_final.fa` | `.agp`（挂载描述）+ 接触图 `.hic` | 每条 scaffold 的构成与方向，能否被接触图支持 |

### 几条必须记住的约定

- **`assembly_info.txt` 是长读长组装最有价值的产物。** 它的 `circular` 与 `repeat` 列直接告诉你「哪些断点是重复区造成的」——这是方法的固有限制，不是参数没调好。有没有这张表，决定你能不能把「组装碎」和「数据不足」区分开。
- **`.gfa` 与中间文件不要删。** 当抛光或桥接之后的序列出现可疑连接时，唯一的核实路径是回到组装图与读长回贴覆盖度。删了就只能重跑。
- **`contigs.fasta` 与 `scaffolds.fasta` 不能混用。** 注释、提交 NCBI、算覆盖度用 contigs；scaffolds 里的 N 会被注释器当作断裂，也会让部分比对工具产生奇怪结果。用 scaffolds 报 N50、用 contigs 做注释、然后在同一张表里引用两者，是这一层最常见的自相矛盾。
- **contig 名不携带生物学信息。** SPAdes 的 `NODE_1_length_123456_cov_42.1` 里的 `cov_` 是 k-mer 覆盖度的近似值，不等于回贴得到的真实覆盖度；用它判断质粒拷贝数或筛污染会系统性偏。真实覆盖度必须把读长回贴后再算。
- **`circular=true` 不等于序列完美。** 它只说明两端能重叠成环；同聚物区的 indel 依然存在。质粒这类小复制子在环化后仍需要抛光与人工核对起点、终点。

### 一个最小可信的组装产物自检

```bash
S=02_assembly/sample_spades

# 1) 产物非空且不是 0 字节（被中断的任务常留下空文件）
for f in "$S/contigs.fasta" "$S/scaffolds.fasta"; do
  [ -s "$f" ] || { echo "EMPTY OR MISSING: $f"; exit 1; }
done

# 2) 统计量与长度分布
seqkit stats -a -T "$S/contigs.fasta" > 10_logs/sample.frame_stats.tsv
seqkit fx2tab -l -n "$S/contigs.fasta" | sort -k2,2nr | head -20 \
    > 10_logs/sample.longest_contigs.tsv

# 3) 记录输入与输出的校验和（可追溯性的最低要求）
md5sum 01_clean/sample_R1.fq.gz 01_clean/sample_R2.fq.gz \
       "$S/contigs.fasta" >> 10_logs/sample.assembly.md5

# 4) 把关键参数从日志里抓出来与命令一起留档
grep -E '^Command line|k values|Mismatch' "$S/spades.log" \
    > 10_logs/sample.spades.params.txt
```

第 3 步与第 4 步看起来像仪式，但它们是「三个月后还能回答『这份 FASTA 是怎么来的』」的唯一保证。

### 数量级的合理性检查（30 秒，能拦下大多数事故）

在进入注释之前，用三个数字与预期对照一次：

| 检查项 | 预期 | 明显偏离时先怀疑什么 |
|---|---|---|
| 总长度 | 与该物种常见基因组大小同量级（多数细菌 2–7 Mbp） | 偏低 → 覆盖度不足或大量 contig 被过滤掉；偏高 → 污染、重复区被多次组装、或质粒被重复计入 |
| contig 数 | 短读长草图常见几十到几百；长读长常见 1–10 | 短读长得到个位数长 contig → 先确认是不是混菌；长读长得几百个 → 先确认预设与读长质量 |
| 最大 contig 长度 | 不应超过该物种染色体长度 | 超过 → 嵌合连接的强信号 |

这三个数字全部可以从 `seqkit stats` 与一次排序得到，成本远低于一次完整的注释返工。

### 中间文件的保留策略

磁盘与可复现性之间存在真实的取舍。一个可用的默认策略：

| 文件 | 保留？ | 理由 |
|---|---|---|
| 最终序列（过滤后 / 抛光后 / 挂载后） | **永久保留** | 下游与归档的唯一依据 |
| 未过滤的原始组装序列 | **永久保留** | 过滤前后的对照，也是复核过滤是否合理的唯一材料 |
| 组装图 `.gfa` | 保留到项目结束 | 排查可疑连接、复核桥接与闭环的唯一一手材料 |
| 运行日志（`spades.log`、`flye.log`、`assembly_info.txt`） | **永久保留，且纳入版本记录** | 参数、k 值、预设、覆盖度估计都在里面 |
| 抛光中间比对文件（BAM） | 可删 | 体积大且可由命令重建；但**命令必须留档** |
| 注释/比对中间目录 | 视流程引擎的缓存策略 | 用 `wf_checkpoint_pipeline` 管，不要手工删 |

一条经验：**删中间文件之前，先确认重建它的命令已经写进日志或流程脚本。** 手工删掉一个 BAM、而重建命令只存在于某个终端历史里，是可复现性最常见的失守点。

## 3.3 工具拼装思路（含选择决策树）

### 先问四个问题，再选工具

1. **读长类型**：只有短读长 / 只有长读长 / 两者都有 / 还有 Hi-C？
2. **下游最敏感的是什么**：序列正确性（SNP、cgMLST、耐药）还是结构正确性（完成图、质粒、染色体结构）？
3. **样本是纯培养物吗**：有污染或混菌时，任何组装器都会产出嵌合，而且指标看起来更好。
4. **重复区有多严重**：rRNA 操纵子拷贝数、IS 元件密度、是否含大型前噬菌体区？

### 决策树

```
样本是宏基因组 / 群落 / 含多个菌株？
└── 立刻离开本章
      用 MEGAHIT / metaSPAdes + 分箱（第 8 章）。
      分离株模式会丢掉低丰度物种的 contig；把群落数据喂给分离株模式
      不会报错，只会得到一份"看起来最好"的嵌合基因组。

只有短读长？
├── 下游关心序列正确性（SNP 分型 / cgMLST / 耐药检出）
│      → SKESA
│         contig 更碎但错误连接更少；快、省内存、适合成百上千样本的批量
├── 关心基因内容完整、希望 contig 尽可能长
│      → SPAdes
│         多 k 值迭代；contig 更长、基因内容更全
└── 想要质粒闭环 / 染色体级结构
       → 短读长做不到。补长读长后用 Unicycler，或接受草图
          （不要用"调参数"来试图解决这个问题）

只有长读长？
├── Nanopore Q20+（R10.4 SUP 等）→ flye --nano-hq
├── Nanopore 早期数据（R9.x）    → flye --nano-raw
├── PacBio HiFi                 → flye --pacbio-hifi
├── PacBio CLR                  → flye --pacbio-raw
└── 选完预设后几乎必然要抛光：
       ONT          → medaka（模型必须与 basecaller / flowcell / 化学版本匹配）
       任意平台      → racon（需 minimap2 产生 PAF）
       HiFi（Q30+）  → 通常不需要抛光，先看前后指标再决定

短读长 + 长读长都有？
├── 目标是完成图（单染色体 + 每个质粒闭环）
│      → Unicycler（默认 conservative）
├── 只想修长读长组装的 indel
│      → Flye → Medaka/Racon →（可选）Pilon/POLCA
└── 长读长覆盖度 < 20x
       → 桥接不可靠，Unicycler 会退化成接近 SPAdes 的水平
          补数据，不要调参

还有 Hi-C？
└── 已完成质量与污染检验 → YaHS / SALSA2 挂载到染色体
       前提：先过滤短 contig，并确认 contig 内部没有残留错误
       结果：必须人工看接触图，不能只看 scaffold 数量

组装碎，断点集中在 rRNA / IS / 噬菌体区？
└── 这是短读长方法的固有限制，不是参数问题
      正确动作：补长读长，或做混合组装；继续调 k 值收效很小
```

### 每个选择的判断依据

**SPAdes 还是 SKESA？** 这不是「哪个更好」，而是「你的下游怕什么」。

- SKESA 在每一步选择最保守的延伸路径，contig 数通常比 SPAdes 多、N50 更低，但错误连接更少；它不做读长纠错，也不用配对信息做 scaffold。
- 所以：下游是 SNP 分型、cgMLST、耐药基因检出时，**一个错误的连接会让整段基因内容错位，而 contig 碎一点不影响基因级结论** → 选 SKESA。
- 下游是注释展示、基因内容比较、需要尽量少的 contig 时 → 选 SPAdes。
- 批量组装成百上千个分离株（单样本分钟级、GB 级内存）→ SKESA 更合适，但**必须显式写 `--contigs_out`**：默认文件名固定，样本一多就会互相覆盖，而且往往到分析末期才发现少了文件。
- 一个必须说清的边界：用 SKESA 的产出讨论「基因组完成度」是不合适的，它的数字会明显低于 SPAdes，这是工具定位差异而非数据质量问题。

**什么时候必须上长读长？** 当瓶颈落在重复区时。rRNA 操纵子、IS 元件、转座子处的塌缩是短读长方法的固有限制，**继续调 SPAdes 的 k 值不会解决它**。可操作的判据是：

> 如果下游结论涉及「复制子个数」「质粒是否成环」「染色体结构」「倒位/易位」，那么只有长读长或混合组装能给出可辩护的答案。如果结论只涉及「某个基因在不在」「某段序列像谁」，草图就够。

**Flye 的预设为什么是这一步最关键的操作？** 因为选错不报错。把 Q20+ 数据用 `--nano-raw`、把老 R9.4 数据用 `--nano-hq`，流程都能跑完，只是组装更碎、小 indel 更多、没有任何警告。这是 Flye 最常见的失败模式。因此：

> 记录「预设 + 碱基识别版本」不是可选项。它决定了结果能不能被解释。

**`--genome-size` 给错会怎样？** 它用于覆盖度估计与重复解析。把质粒算漏、或按近缘物种估，会改变覆盖度归一化，进而影响**哪些重复被判为可解析**，最终改变 contig 断点。建议先用 Mash/k-mer 估一个数量级正确的值，并把最终填入的值写进方法。

**抛光到底修什么？** 长读长的错误以同聚物区 indel 为主，会让编码区出现假移码与提前终止。抛光就是把碱基级错误修回来。它**不修结构错误**——嵌合连接、错误桥接在抛光后只会变得更「干净」，更难被发现。所以：

| 抛光路线 | 适用对象 | 关键前提 | 不适用的情况 |
|---|---|---|---|
| Medaka | 仅 Nanopore | 模型必须与 basecaller、flowcell、化学版本匹配，否则可能比 Racon 更差 | PacBio 数据（不会得到有意义的结果） |
| Racon | ONT 与 PacBio 通用 | 每轮必须把读长重新比回**当前**序列 | 想修结构错误时 |
| Pilon / POLCA | 长读长组装 + 高质量短读长 | 覆盖度经验上不宜低于约 20x；必须先比对再抛光 | HiFi 组装（收益小、可能引入不一致） |
| 不抛光 | HiFi（Q30+）组装 | 用 QUAST/BUSCO 前后对比决定，而不是按惯例 | 编码区结论要求极高且数据支持时 |

**抛光不是「轮数越多越好」。** 第 1 轮收益最大，第 2 轮之后通常进入噪声范围；过度抛光可能引入新错误。判断是否成功要看**方向一致的一组指标**：

```bash
# 抛光前后对比：contig 数、总长度、N50、完整基因数
seqkit stats -a -T draft.fasta polished.fasta > 10_logs/polish_stats.tsv
# 期望的方向：总长度小幅收缩（多余小 indel 被修正）、完整基因数略有回升
```

如果总长度大幅缩短（例如超过 5%），应当回头检查组装本身，而不是继续抛光。

**Hi-C 什么时候值得做？** 当长读长不足以把多条复制子分开时（例如双染色体、多个大质粒混在一起）。两条必须遵守的纪律：

1. Hi-C **只解决顺序与方向，不修正 contig 内部的错误**。一条嵌合 contig 被挂进染色体后，问题从「一个 contig 的错误」升级为「染色体结构错误」，而且很难回溯。所以挂载前必须完成污染与错误检验（`asmqc_quast` / `asmqc_busco` / `asmqc_checkm2` / `asmqc_gunc` / `asmqc_ideel`）。
2. 结果**必须人工看接触图**：染色体条数是否符合该物种的预期、是否有明显的越界连接、复制终止区附近是否出现反常强信号。只看 scaffold 数量变少、N50 变高就宣布成功，是这一类分析里最危险的用法。

### 三条端到端路线（可直接当骨架用）

**路线 A：只有短读长，目标是分型与耐药筛查（最常见）**

```bash
S=sample; T=16

# 1) 组装：序列正确性优先 → SKESA
skesa --reads 01_clean/${S}_R1.fq.gz,01_clean/${S}_R2.fq.gz \
      --cores $T --contigs_out 02_assembly/${S}.skesa.fasta \
      > 10_logs/${S}.skesa.log 2>&1

# 2) 长度过滤（NCBI 提交下限 200 bp；注释通常需要更长）
seqkit seq -m 500 -w 0 02_assembly/${S}.skesa.fasta \
    -o 02_assembly/${S}.filtered.fasta

# 3) 过滤前后统计（报告里必须说清用的是哪一版）
seqkit stats -a -T 02_assembly/${S}.skesa.fasta \
    02_assembly/${S}.filtered.fasta > 10_logs/${S}.filter_stats.tsv

# 4) 组装统计与质量评估 → 第 4 章
#    quast.py / busco / checkm2 / gunc
```

**路线 B：短读长 + 长读长，目标完成图**

```bash
S=sample; T=16

# 1) 长读长过滤（保留长尾；覆盖度按碱基数算）
filtlong --min_length 1000 --keep_percent 95 \
    00_raw/${S}.ont.fastq.gz | gzip > 01_clean/${S}.ont.filt.fq.gz

# 2) 混合组装（默认 conservative；碎片多通常反映数据不足）
unicycler -1 01_clean/${S}_R1.fq.gz -2 01_clean/${S}_R2.fq.gz \
          -l 01_clean/${S}.ont.filt.fq.gz \
          -o 02_assembly/${S}_unicycler -t $T

# 3) 立刻核对结构：contig 数是否符合预期（单染色体 + N 个质粒）
seqkit stats -a 02_assembly/${S}_unicycler/assembly.fasta

# 4) 用短读长证据复核桥接与闭环是否引入了局部错误 → asmqc_ideel
# 5) 用接触图或读长回贴覆盖度确认没有可疑连接
```

**路线 C：只有长读长，需要尽可能高的编码区准确性**

```bash
S=sample; T=16

# 1) 组装（预设必须与碱基识别版本匹配）
flye --nano-hq 01_clean/${S}.ont.filt.fq.gz --genome-size 5m \
     --out-dir 02_assembly/${S}_flye --threads $T

# 2) 先看结构：环化与重复标记
head 02_assembly/${S}_flye/assembly_info.txt

# 3) 长读长共识抛光（模型必须匹配；否则可能比 Racon 更差）
medaka tools list_models
medaka_consensus -i 01_clean/${S}.ont.filt.fq.gz \
     -d 02_assembly/${S}_flye/assembly.fasta \
     -o 02_assembly/${S}_medaka -t $T -m <model_name>

# 4) 需要编码区高准确度时再叠一层短读长抛光
#    Pilon 或 POLCA；第二轮前必须重新比对
polca.sh -a 02_assembly/${S}_medaka/consensus.fasta \
     -r "01_clean/${S}_R1.fq.gz 01_clean/${S}_R2.fq.gz" -t $T

# 5) 核查残留 indel 与被打断的 ORF → asmqc_ideel
```

### 反模式：这些做法看起来合理但会带来系统性偏差

| 反模式 | 为什么错 |
|---|---|
| 先组装再查污染 | 混菌组装的指标最好看，你会失去怀疑它的理由 |
| 用 `--bold` 让 contig 数变少 | 只是把不确定性变成看不见的错误连接；统计量变好，结论可能完全错 |
| 反复微调 k 值来解开 rRNA 操纵子 | 重复区塌缩是方法固有限制，不是参数问题 |
| 用同一批短读长再抛光一次「提升」SPAdes 结果 | 没有新信息，只会把序列换成另一套，让前后结果不可比 |
| 混用 contigs 与 scaffolds 的统计量 | 统计量必须来自同一份序列 |
| 把长读长喂给 fastp / Trimmomatic | 它们按短读长模型修剪，会破坏读长的长度优势 |
| 把 PacBio 读长喂给 Medaka | 不会得到有意义的结果；PacBio 用 Racon 或平台自带的共识流程 |
| 用抛光来「救」低覆盖度数据 | 证据不足的位点会按统计倾向被改动，等于把噪声固化成错误 |
| 用 Hi-C 去「修」contig 内部的错误 | Hi-C 只给顺序与方向，会把内部错误固化并放大到染色体级别 |
| 在没看接触图的情况下采用挂载结果 | scaffold 数变少、N50 变高完全不能作为成功判据 |

### 路线速查表

把四个判断问题压缩成一张表，用于快速定位该走哪条路线：

| 数据 | 目标 | 路线 | 主要代价 |
|---|---|---|---|
| 短读长 | 分型、耐药、基因内容 | SKESA → 长度过滤 | contig 较碎，不适合结构结论 |
| 短读长 | 注释展示、尽量少的 contig | SPAdes → 长度过滤 | 相同覆盖度下运行时间与内存更高 |
| 短读长 + 长读长 | 完成图（染色体 + 质粒闭环） | Unicycler（conservative） | 慢，依赖多，需复核桥接 |
| 短读长 + 长读长 | 编码区最高准确度 | Flye → Medaka/Racon → Pilon/POLCA | 三轮抛光，需逐步核对指标方向 |
| 长读长（HiFi） | 完成图，尽量少抛光 | Flye `--pacbio-hifi` →（按需）Racon | HiFi 数据成本高，覆盖度不足时仍会碎 |
| 长读长（ONT） | 完成图 + 结构结论 | Flye `--nano-hq` → Medaka（匹配模型）| 模型匹配错误会静默降低质量 |
| 长读长 + Hi-C | 多复制子排序定向 | 长读长组装 → 质量检验 → YaHS/SALSA2 | 必须人工看接触图；上游错误会被固化 |
| 宏基因组 | MAG | MEGAHIT / metaSPAdes → 分箱（第 8 章） | 组装质量是 MAG 质量的天花板 |

## 3.4 关键参数取舍

### 覆盖度：给数字，也给理由

| 数据类型 | 常见目标覆盖度 | 理由 |
|---|---|---|
| 短读长（Illumina） | 50–150x | 低于 50x 时重复区无法被足够读长跨越，contig 会更碎；高于 150x 后收益迅速递减，反而放大 PCR 重复带来的错误证据 |
| 长读长（Nanopore / PacBio） | 30–50x | 长读长的价值在跨度不在深度。低于约 20x 时桥接与重复解析不可靠，Unicycler 的桥接会退化成接近 SPAdes 的水平 |
| 短读长抛光 | ≥ 20x | 证据不足的位点会按统计倾向被改动，等于把噪声固化成错误 |

两条容易忘的换算：

- **长读长的覆盖度按碱基数算，不是按读长条数。** 用条数判断会严重低估。
- 需要削减数据量时**按碱基覆盖度下采样，而不是按读长条数**。`filtlong --target_bases` 比 `--keep_percent` 更直观；它还会优先保留对组装最有价值的读长（长读长、能覆盖其他读长 k-mer 的读长）。

估算公式与一个具体例子：

```
短读长覆盖度 ≈ 读长数 × 读长(bp) × 2 / 基因组大小(bp)      # 双端，R1+R2 都要算
长读长覆盖度 ≈ 总碱基数 / 基因组大小(bp)
```

假设基因组 5 Mbp，读长 2×150 bp：

| 目标覆盖度 | 需要的 read pairs |
|---|---|
| 50x | 约 0.83 M pairs |
| 100x | 约 1.67 M pairs |
| 150x | 约 2.5 M pairs |

先算一次这个数字，再去检查数据量，能提前发现两类问题：数据量只有 20x（组装会很碎，属于数据不足而不是参数问题），或数据量有 1000x（需要下采样，否则组装时间与内存消耗不成比例，而且 PCR 重复会放大错误证据）。

### SPAdes

| 参数 | 建议 | 为什么 |
|---|---|---|
| `-k` | 用默认多组（常见 21,33,55,77），**项目内固定并记录** | k 必须明显小于读长；改变 k 列表会让结果与既有流程不可直接比较 |
| `--isolate` | 高覆盖度纯培养物开启 | 针对单一分离株的严格模式；与 `--meta` 是两套完全不同的模式，不能混用 |
| `--careful` | 视情况 | 减少最终 contig 中的错配与短 indel，代价是运行时间；与 `--isolate` 的关系以官方文档为准 |
| `--cov-cutoff` | 污染或杂音多时给具体值或 `auto` | **会误删低拷贝质粒**：高拷贝质粒覆盖度远高于染色体，低拷贝大质粒可能低于染色体，一刀切会优先删掉真正的质粒 |
| `--only-assembler` | 只在内存实在不足时 | 跳过读长纠错，保留更多错误碱基 |
| `-m` | 按机器显式设置 | 设得过小不会自动降级，而是直接失败 |
| `-t` | 按核数显式设置 | 默认 16；批量流程里不设置会低估资源需求 |

两个操作细节：SPAdes **拒绝把结果写进非空输出目录**，重跑会直接报错退出（换 `-o` 目录、清空旧目录，或用续跑参数从某个 k 值继续——确切用法以官方文档为准）；`contigs.fasta` 与 `scaffolds.fasta` 的选择见 3.2。

### SKESA

| 参数 | 建议 | 为什么 |
|---|---|---|
| `--reads` | 逗号分隔文件列表；gzip 可直接读 | 不必先解压 |
| `--cores` | 显式设置 | 否则批量流程会低估资源需求 |
| `--contigs_out` | **必填** | 默认名固定，串行脚本里极易被下一个样本覆盖 |
| `--kmer` | 批量项目固定并记录 | k-mer 列表随读长与版本变化；不同 k 的结果不可直接比较 |
| 最小 contig 长度选项 | 一般不用，改用 `asm_filter_contigs` | 调高只是不输出短 contig，不改变组装本身；过滤统一在组装后做便于留痕 |

一句经验：超高高覆盖度（数百 x）不会让 SKESA 更好，只会更慢。需要削减数据量时应按碱基覆盖度下采样。

### Flye

| 参数 | 建议 | 为什么 |
|---|---|---|
| `--nano-hq` / `--nano-raw` / `--pacbio-hifi` / `--pacbio-raw` | 必选其一，与平台和碱基识别版本匹配 | 选错不报错但结果系统性变差 |
| `--genome-size` | raw 模式必填；先用 Mash 估一个数量级正确的值并记录 | 用于覆盖度估计与重复解析；错一倍会改变哪些重复被判为可解析 |
| `--asm-coverage` | 默认自动；若要限制，注意代价 | 限制用于组装的覆盖度以省时间，降得太多会削弱重复解析（以官方文档为准） |
| `-i / --iterations` | 保持默认 1 | Flye 的内置抛光不足以替代 Medaka/Pilon，不要靠调它代替抛光 |
| `--meta` | 群落数据才开 | 单一分离株样本不要开启 |
| `-t` | 显式设置并记录 | 长读长组装的耗时对线程很敏感 |

### Unicycler

| 参数 | 建议 | 为什么 |
|---|---|---|
| `--mode` | 默认 `conservative` | 默认档留下来的碎片通常反映数据不足，而不是参数不够猛。切到 `--bold` 只是把不确定性变成看不见的错误连接 |
| `--keep` | 排查可疑连接时开启 | 保留中间文件（SPAdes 图、桥接过程），磁盘占用成倍增加 |
| `--no_pilon` | 数据量大或短读长质量差时 | 跳过最终短读长抛光，先跑通结构再单独评估 |
| `-l / --long` | 决定这是混合组装还是「SPAdes + 桥接」 | 不给长读长时它没有实质优势 |

一个部署经验：Unicycler 依赖 `spades.py`、`racon`、`pilon`（Java）、`bowtie2`、`samtools`、BLAST+ 一整套外部程序，缺一个就会失败，而且报错形式可能是「找不到 java」这类与生信无关的信息。容器化运行比逐个 conda 安装省事得多。

### 抛光

| 参数 | 建议 | 为什么 |
|---|---|---|
| Pilon `--frags` / `--jumps` / `--unpaired` | 按文库类型选择 | 类型给错会得到错误的插入片段模型，改动结果不可信 |
| Pilon `--changes` | **必须开启** | 输出逐位点改动清单，否则无法核查抛光改了什么 |
| Medaka `-m` | 必须显式指定；以 `medaka tools list_models` 的输出为准 | 模型与数据不匹配是最难察觉的错误：流程不报错也能跑完，但共识质量可能低于 Racon |
| Racon 比对预设 | `map-ont` / `map-pb` | 预设与平台不匹配会显著降低比对率，抛光效果随之变差 |
| 迭代轮数 | 1–2 轮 | 第 2 轮之后提升通常已在噪声范围内；过度抛光可能引入新错误 |
| 抛光用读长过滤强度 | 轻度或无过滤 | 抛光需要覆盖全部组装区域；大幅削减后的子集会让部分区域被改动而缺乏证据 |
| 是否去重 | 高覆盖度数据先去重 | PCR 重复会放大 Pilon 的证据强度，让某些位点被过度「修正」 |

### Hi-C 挂载

| 参数 | 建议 | 为什么 |
|---|---|---|
| 酶切位点（SALSA2 `-e`；YaHS 相关选项） | 必须与建库所用的限制酶一致（如 `GATC`） | 给错会让连接信号无法解析；YaHS 新版已简化，处理方式以官方文档为准 |
| contig 级纠错开关（YaHS `--no-contig-ec` 等） | 明确其状态 | 内置纠错会改动 contig 序列；要与未挂载版本严格比较时必须知道它有没有被改动 |
| 比对排序方式 | 按读长名排序 | Hi-C 需要配对的两端信息，排序方式给错会导致没有可用连接 |
| 最小 contig 长度 | 先过滤再挂载 | 过短的 contig 在 Hi-C 中几乎没有信号 |
| Juicer 接触图 | 建议必做 | 生成 `.hic` 后可在 Juicebox 中人工核查；命令与版本以官方文档为准 |

### contig 过滤（`asm_filter_contigs`）

| 参数 | 建议 | 为什么 |
|---|---|---|
| `seqkit -m` | 500 | NCBI 提交的下限是 200 bp；注释与 MAG 分析常用 500–1000。**阈值必须在项目内统一** |
| `seqkit -w 0` | 开启 | 不换行输出序列；部分老工具对多行 FASTA 的处理有差异 |
| 覆盖度阈值 | 先看 per-contig 覆盖度分布再定 | 双峰常意味着污染或质粒；**没有通用值**，套用别人的数字是最常见的错误 |
| 分类证据过滤 | 按比对/分类结果剔除明显不属于目标类群的 contig | 用「无比对命中就删」会误删新物种或参考库缺失的环境菌序列 |
| 输入序列版本 | 优先过滤 contig 级序列 | 含 N 的 scaffold 会让长度统计虚高 |
| 版本记录 | 过滤前后都留 md5 与统计 | 过滤会改变 contig 数、总长度与 N50，报告里必须说清用的是哪一版 |

```bash
# 长度过滤 + 前后对比（把两版序列都留下）
seqkit seq -m 500 -w 0 02_assembly/${S}.contigs.fasta \
    -o 02_assembly/${S}.filtered.fasta
seqkit stats -a -T 02_assembly/${S}.contigs.fasta \
    02_assembly/${S}.filtered.fasta > 10_logs/${S}.filter_stats.tsv
```

### 参数记录清单（每个组装样本都要有）

```
软件与版本 | 模式/预设 | k 值列表或 k-mer 设置 | 线程与内存
输入读长文件 + md5 | 覆盖度（按碱基算）| 参考/数据库版本（若用到）
输出序列 md5 | 过滤阈值 | 抛光轮数与所用读长
```

缺任何一项，这份组装都无法在半年后被解释。

## 3.5 常见坑

这一节讲**跨步骤的系统性问题**，而不是单条命令的参数错误。单条参数问题在各模块的 pitfalls 里已经写得很细。

### 坑 1：组装质量是注释质量的天花板

这不是一句比喻，而是有具体机制的：

- 一个被 contig 边界截断的基因，在 Prokka/Bakta 里会得到两种命运之一——被预测成一个短 ORF（产生一个**假基因家族**），或直接消失（产生一个**假缺失**）。两种都会污染下游的存在/缺失矩阵。
- 长读长同聚物区的框架移码会让一个真基因被拆成两个 ORF。在泛基因组里表现为「一对互补缺失的假家族」，这种模式在热图上非常显眼。
- 因此：**任何基于「基因存在 / 缺失」的结论，其可靠性上限由组装决定。** 如果两个菌株的组装质量差异明显（一个染色体级、一个几百个 contig），它们之间的基因内容差异里必然混着技术性差异。规范做法是按组装质量分层分析，或至少在方法里明确说明这一局限。

同样地，组装质量也是**分型分辨率**与**共线性结论**的天花板：第 7 章会讲到，草图的 contig 断点会被共线性工具记成「易位」，看起来结构差异巨大，实际只是没拼通。

### 坑 2：模式选择错误是一种「不报错的错误」

`--meta` 与 `--isolate`、Prodical 的 `-p single` 与 `-p meta`、Flye 的 `--nano-raw` 与 `--nano-hq`、FastTree 的 `-nt` 与默认蛋白模式——这些都属于同一类问题：**选错不报错，只是结果系统性变差。**

应对方式不是背下每一组参数，而是养成一条习惯：

> 每一个「模式 / 预设」类参数都要写进日志，并在流程里显式给出，不让默认分支替你决定。

可操作的检查：跑完之后回看日志，确认工具实际使用的模式与你以为的一致。SPAdes 的 `spades.log`、Flye 的 `flye.log` 都会打印实际参数。

### 坑 3：序列版本混用，而且很难被发现

同一个样本在流程中会同时存在：未过滤的 contigs、过滤后的 contigs、抛光版本、挂载后的 scaffolds、注释工具重命名过的 contig。它们的坐标体系与序列名可能全都不同。具体危险点：

- Prokka 会把 contig 名重写成 `contig00001` 之类，注释坐标不再与原始组装的名字对应。之后把注释结果与原始 contig 或其它工具结果合并时，必须先确认名字映射，否则坐标对错位置却看不出来。
- Hi-C 挂载后的坐标体系与挂载前不同（序列被重排、插入 N）。注释与比较分析必须统一用挂载后的 FASTA 重做，混用两套坐标会让基因位置与共线性结论互相矛盾。
- 抛光会改变总长度、contig 边界，甚至连接或拆分 contig。**未抛光版本必须保留**，报告里要说明提交与分析用的是哪一版。同一菌株的不同版本不可互换。
- 过滤前后必须留下明确的版本关系（文件名、md5、命令与日志）。下游一旦混用两个版本，基因坐标与注释会互相矛盾，而且极难追查。

一个便宜的防御措施：只接受带明确版本后缀的文件名（`sample.filtered.fasta`、`sample.polished.r2.fasta`），并禁止出现 `sample.final.fasta` 这种名字。

### 坑 4：把「调参」当成「解决问题」

遇到组装碎，先做诊断，再决定是调参还是补数据。三类典型症状的判别：

| 症状 | 更可能的原因 | 正确动作 |
|---|---|---|
| contig 在相同位置反复断开，且断点集中在 rRNA / IS / 噬菌体区 | 重复区的固有限制 | 补长读长或做混合组装，不要继续调 k |
| 大量低覆盖 contig，覆盖度分布呈双峰 | 污染、混菌，或测序深度不足 | 先做分类筛查确认物种组成；是污染就剔除，是深度不足就补数据 |
| 总长度明显大于预期基因组大小 | 污染、重复区被分别组装多次、杂合区被拆开 | 结合 duplication ratio、CheckM2/BUSCO 与分类结果判断 |
| 单条超长 contig + 覆盖度异常均匀 + 指标极好 | 混菌导致的嵌合组装 | 回到读长层面做筛查 |
| 抛光后总长度大幅缩短（> 5%） | 组装本身有问题，或者输入读长来源不一致 | 回头检查组装，而不是继续抛光 |

### 坑 5：组装指标是相对量，不是成绩单

`N50` 依赖 contig 长度阈值（QUAST 默认只统计不短于 500 bp 的 contig），也依赖用的是 contig 还是 scaffold。跨工具、跨论文比较 N50 之前，必须先确认三件事：阈值、序列类型（contig / scaffold）、以及是否做过长度过滤。

`scaffolds.fasta` 里的 N 会让 N50 变好、最长序列变长，**但不代表信息更多**。用 scaffolds 报统计、用 contigs 做注释，再把两者混着引用，是这一层最常见的自相矛盾。

一个更严格的判据：把 `contig N50` 当验收标准之前，先写清阈值来源与序列版本，否则不同人看同一张表会得出不同结论。

### 坑 6：长读长的抛光证据链容易断

抛光需要「读长 + 当前序列」的比对，任何一侧换了都必须重新比对。第二轮抛光前忘记重新比对，等于把第一轮重复计算一次并再次改动序列，结果无法解释。

同样需要警惕的是**污染读长参与抛光**：若抛光用的短读长来自不同批次、不同文库或混有污染，抛光会把污染等位基因**固化**进基因组。这比不抛光更糟，因为它看起来更可信。抛光前先确认读长的物种纯度与来源一致性。

### 坑 7：把「合并了多个菌株」的组装当成好结果

这是最危险的坑，因为它与传统判据完全相反。若读长里混了两个近缘菌株，组装器会把两套基因内容合并成一套，得到「单条长 contig、无碎片、N50 极高」的结果——**指标最好的一次往往是最不可信的一次**。唯一可靠的防线是在组装前做读长层面的分类筛查，而不是事后看指标。

一个补充判据：如果组装总长度明显超过该物种的常见基因组大小，且没有明显的质粒或重复区解释，应当先怀疑污染，而不是先庆祝。

### 坑 8：把完成图当作目标本身

「拿到完成图」在细菌基因组学里是常见目标，但它只在需要结构结论时才值得付出成本。对于物种鉴定、耐药筛查、基因内容比较，一张高质量草图完全够用。把预算花在把 40 个 contig 降到 5 个 contig 上，而不是增加样本数或做表型验证，通常是资源错配。

反过来的错误同样常见：**用草图去下结构结论**。复制子个数、质粒是否成环、染色体重排，这些都需要完成图或至少染色体级组装来支撑。

### 坑 9：不区分「生物学断点」与「技术性断点」

组装碎不一定全是技术问题。真实的基因组里确实存在难以跨越的区域（例如两端高度相似的 rRNA 操纵子），长读长也可能在这里断开。区分方式：

- Flye 的 `assembly_info.txt` 会把重复区导致的断点标出来；
- 读长回贴后，看断点两侧的覆盖度是否突然升高（重复区塌缩的典型特征）；
- 与近缘完成图比较，看断点位置是否落在已知的可移动元件或 rRNA 区。

区分开之后，报告里可以写「本组装的 12 个断点中 9 个位于 rRNA 操纵子或 IS 元件区，属于方法的已知限制」，而不是笼统地说「组装较碎」。

### 坑 10：把 `--meta` / 分离株的边界当成参数细节

这是第 3 章与第 8 章的分界线，也是实际项目里最常见的错配：**分离株组装与宏基因组组装是两条技术路线，不是同一工具的两种参数。** 把宏基因组数据喂给分离株模式不会报错，但会丢掉低丰度物种；把纯培养物喂给宏基因组模式则会得到过度保守、基因数偏少的注释。判断依据是样本来源，不是数据量大小。

### 坑 11：跨样本比较时，忘了组装本身也是变量

当你把 30 个菌株的组装放在一起做泛基因组或存在/缺失比较时，**组装流程的差异会直接变成「生物学差异」**。典型来源：

- 不同批次用了不同的组装器（早期用 SPAdes，后期换 SKESA）——contig 数与断点位置全变，截断基因的比例随之变化。
- 不同批次用了不同的过滤阈值（这一批用 200 bp，那一批用 500 bp）——「缺失基因」的数量会凭空变化。
- 不同批次的读长长度或平台不同（150 bp 与 250 bp）——同一位点能否被跨越不同。
- 不同批次的长读长覆盖度差异大——抛光效果不同，框架移码比例不同。

这类差异**不会报错，也没有明显的统计信号**，只会在结果里表现为「某些菌株的附属基因特别多」。可操作的防线只有一条：**同一比较项目内的所有基因组必须走同一条组装与过滤流程**，并在方法里写明版本与阈值。若历史数据无法重跑，应在报告中按批次分层分析，或明确说明这一局限。

这一条与第 7 章的「注释必须同源」是同一个问题的两个层面：**跨基因组比较的前提是上游流程一致**，而组装是这条链上最早、也最难事后修正的一环。

## 3.6 与面板模块 id 的对应

| 模块 id | 一句话说明 |
|---|---|
| `asm_spades` | 短读长组装的事实标准；多 k 值迭代，contig 更长、基因内容更全 |
| `asm_skesa` | NCBI 的保守型短读长组装器；更快更省内存，序列正确性优先时选它 |
| `asm_flye` | 长读长从头组装；预设必须与平台和碱基识别版本匹配，断点成因记录在 `assembly_info.txt` |
| `asm_unicycler` | 短读长 + 长读长混合组装，追求质粒闭环与染色体级结构；三档模式是核心取舍 |
| `asm_medaka_polish` | 长读长共识抛光（Medaka / Racon），修同聚物区 indel；不修结构错误 |
| `asm_short_polish` | 用短读长抛光长读长组装（Pilon / POLCA），目标是编码区准确性 |
| `asm_hic_scaffold` | Hi-C 把 contig 排序定向到染色体级别；只解决顺序，不修内部错误 |
| `asm_filter_contigs` | 按长度与证据精简 contig；阈值会改变所有组装统计量 |
| `qc_quality_trim_long` | 长读长过滤；不要用 fastp 修剪长读长，过滤过狠会丢掉跨越重复区的长读长 |
| `qc_contamination_screen` | 读长层面的污染筛查；它是本章流程的第一道闸门 |
| `qc_dedup_reads` | 高覆盖度数据在组装与抛光前去重，避免证据强度被高估 |
| `util_seqkit` | 序列文件的通用操作；统计、过滤、格式转换的日常工具 |
| `wf_reproducibility` | 版本、数据库、命令与校验和的记录规范 |
| `wf_checkpoint_pipeline` | 断点续跑；长读长组装与抛光时间长，续跑比从头重跑省得多 |
| `meta_megahit` | 宏基因组组装的入口；提醒你分离株与群落是两条路线 |
| `meta_metaspades` | SPAdes 的宏基因组模式；与 `asm_spades` 不是同一套参数 |
