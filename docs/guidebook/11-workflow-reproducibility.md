# 第 11 章 工作流引擎与可重复性

## 11.1 这一层要回答什么问题

前面十章讲的是「怎么算对」。这一章讲的是另外三件事：

1. **怎么把十几个步骤串起来，而不是每次手工敲？**
2. **跑到第八步失败时，怎么从第七步继续，而不是从头再来？**
3. **半年后（或审稿人问起时），怎么回答「这个结果是怎么算出来的」？**

这三个问题看起来是工程问题，但它们直接决定科学产出的可靠性。一个只跑通过一次的流程，实际上**只产出了一次结论，而没有产出可验证的方法**。更现实的问题是：如果重跑一次的成本是三天，你就不会去改那个可疑的参数——于是错误留在了结果里。

### 可重复性的最低标准

可重复性听起来是个很高的目标，但它的**最低要求**只有四项，而且每一项的实现成本都很低：

```
软件版本  +  数据库版本  +  输入校验和  +  实际命令
```

| 项 | 怎么记录 | 不记的后果 |
|---|---|---|
| 软件版本 | 环境锁文件 + 工具 `--version` 输出 | 换了版本结果变了，无法判断是参数问题还是版本问题 |
| **数据库版本** | 下载日期 + 来源 URL + 提供方公布的校验和 | 同一版工具配不同库会给出不同结论，且**完全无法察觉** |
| 输入校验和 | `sha256sum` / `md5sum` 清单 | 无法区分「同一份数据跑了两次」与「数据被人换过」 |
| 实际命令 | 引擎日志 / `trace` / `shell` 历史 | 参数写的是什么只有当时那个人知道 |

这四项里，**数据库版本的权重常高于软件版本**，而它恰恰是最常被漏掉的一项。

值得说清的是，可重复性有三个强度等级，它们的成本差别很大，别把目标定错：

| 等级 | 目标 | 需要做到 | 现实中的达成率 |
|---|---|---|---|
| ① 自己能追溯 | 半年后你还能说清这个结果是怎么来的 | 四项俱全，落成文件 | 应该 100% 做到，成本只有几行脚本 |
| ② 别人能重跑 | 同实验室的人按 README 能跑出相同结果 | ① + 环境锁文件 + 清单驱动 + 断点判据 | 需要刻意的工程习惯，值得投入 |
| ③ 任何人能重跑 | 陌生人拿到代码与数据也能复现 | ② + 容器镜像 + 数据库一并归档 + 完整测试 | 成本很高，只在关键流程上追求 |

**多数项目的合理目标是 ②。** 追求 ③ 时常见的失败模式是：花大量时间做容器与 CI，却没有记录数据库版本——结果连 ① 都没达到。

举三个具体的例子说明为什么：

- 同一版 **Kraken 2**，配标准库与配 plusPF 库，同一个样本的物种组成会有显著差异——因为可检出的物种范围不同
- 同一版 **GTDB-Tk**，配 GTDB R207 与 R220，同一个基因组的分类可能落到不同的属
- 同一版 **Bakta** 或 **Prokka**，配不同版本的数据库，注释到的基因数量与功能描述都会变

软件版本记录得再仔细，数据库版本缺失一样无法复现。这一点在注释与分类类的分析里是**第一位的**，而不是次要项。

### 引擎选型的判断依据：Snakemake 还是 Nextflow

这两个引擎解决同一类问题（声明式规则 + 依赖图 + 自动并行 + 断点续跑），选型不该看「哪个更流行」，而看你**流程的重心在哪**。

| 判断依据 | 偏 Snakemake | 偏 Nextflow |
|---|---|---|
| 你描述流程的方式 | 以**文件与依赖图**为中心：`input` → `output` 就是依赖关系 | 以**数据流与 channel** 为中心：process 之间用 channel 传递 |
| 你熟悉的语言 | Python（rule 就是 Python，可直接写 `run:` 块） | Groovy 方言（需要另外学一点语法） |
| 需要复用现成流程 | 无对应生态 | **nf-core** 有大量已发表的标准化流程可直接跑 |
| 执行平台 | 本地 + 单集群（profile 切换） | 本地 / Slurm / SGE / AWS Batch / GCP，**同一份流程多平台** |
| 容器集成 | `container:` 指令，配合 `--use-singularity` | `container` 是每个 process 的一等属性，与 nf-core 配套最成熟 |
| 学习曲线 | 平缓（会 Python 就能开始） | 陡一些（channel 的惰性求值需要时间建立直觉） |

一句话的判断规则：**主要跑在本地或单个集群、流程是自己写的、且偏好 Python → Snakemake；需要复用 nf-core 的现成流程，或同一份流程要跑在集群与云上 → Nextflow。**

### 什么时候不需要引擎

引擎不是免费的。写一份 Snakefile 需要为每条规则声明准确的输入输出，而声明不完整会带来**比手工脚本更难查的问题**（引擎认为已完成而跳过）。以下情况用脚本更合适：**一次性探索分析**（只跑一次，不打算重跑）；**步骤少于 5 个且以后不会改**（`make` 甚至一个带断点的 bash 脚本就够）；**还在确定方法学的阶段**（流程每天都在变，过早固化会拖慢探索）。

反过来说，出现下面任何一条就该上引擎：流程需要重复运行（换个样本、换个参数、补一批数据）；步骤超过 5 个或样本超过 10 个；需要交接给他人；需要在集群上跑或需要中断后恢复。

`wf_checkpoint_pipeline` 提供了一个**不上引擎也能断点续跑**的手工骨架：每一步产出独立落盘，下一步开头检查产物是否存在且非空。它不如图引擎优雅，但比「从头再跑」好得多，而且可以作为过渡方案——先用它把步骤边界划清楚，再改写成 rule。

## 11.2 输入、输出与中间文件长什么样

### 输入：三样东西

| 输入 | 形态 | 要求 |
|---|---|---|
| 已经手工验证过的命令 | 终端里真正跑通过的完整命令 | **先手工跑通一步，再写进 rule**。没验证过的命令行写进流程只会把调试成本推后 |
| 样本清单 | `samples.tsv` | 一行一个样本，含文件路径与分组属性；这是批量的驱动源 |
| 上次运行的日志与资源用量 | `10_logs/`、`sacct` 输出、`trace.txt` | 用来判断哪里慢、哪里吃内存，以及这次该申请多少资源 |

样本清单值得单独强调：**批量的正确做法是清单驱动**，而不是在脚本里硬编码样本名。增加样本时只改表、不改代码，同时也让「这次跑了哪些样本」变成可追溯的事实。

```
sample	r1	r2	group	batch
S1	00_raw/S1_R1.fq.gz	00_raw/S1_R2.fq.gz	control	b1
S3	00_raw/S3_R1.fq.gz	00_raw/S3_R2.fq.gz	treat	b2
```

两条来自实际经验的约束：**样本名统一用下划线，不含空格、连字符与点**（Snakemake 的通配符遇到这些字符时匹配会出问题，而错误信息通常指向别处）；**排序方式要固定**（建议 `LC_ALL=C sort`——字母序会把 `sample10` 排在 `sample2` 前面，R1 与 R2 列表若用不同排序会静默错配样本）。

### 目录布局

```
project/
├── 00_raw/                 # 只读，永不修改
├── 01_clean/  02_assembly/  ...    # 各步骤产物，全部由流程写出
├── 09_results/             # 最终结果与图
├── 10_logs/                # run_manifest.tsv、checksums.sha256、slurm/、引擎日志
├── refs/                   # 参考数据库与索引（单独管理版本）
├── envs/                   # 环境定义与锁文件
├── scripts/                # 规则调用的小脚本（不要写进 rule 里）
├── workflow/               # Snakefile / main.nf / config
└── work/                   # Nextflow 的缓存目录（与 results 物理分开）
```

两条纪律：**① `work/`（缓存）与结果目录必须物理分开**——清理输出时误删缓存会让 `-resume` 完全失效，反过来清理缓存时误删结果就等于白跑。**② `refs/` 单独管理版本**——参考数据库体积大、更新频繁，把它与代码分开的原因见 11.5 的坑 2。

### 中间文件：流程本身的产物

| 文件 | 类型 | 作用 |
|---|---|---|
| `Snakefile` / `main.nf` + `nextflow.config` | 脚本 | 流程定义。引擎与集群/容器配置分离 |
| `envs/*.yaml` + `envs/*.lock.yaml` | 脚本 | 环境定义与**完整依赖树锁文件**，可复现性的实际载体 |
| `containers.tsv` | 通用表格 | 每个步骤用的镜像，**记 digest 而不是 tag** |
| `run_manifest.tsv` / `checksums.sha256` | 日志与统计报告 | 溯源清单与输入校验和，随结果归档 |
| `dag.pdf` | 报告/图表 | 依赖图；说明「分析是怎么组织的」最直观的材料 |
| `.nextflow.log` / `.snakemake/log/` | 日志 | 引擎日志，含实际执行的每条命令 |
| `trace.txt` / `report.html` | 日志与统计报告 | 每任务的命令、耗时与内存峰值 |
| `batch_status.tsv` | 日志与统计报告 | 逐样本状态；「只重跑失败样本」的依据 |

### 溯源清单长什么样

`wf_reproducibility` 的输出应该是一张**人能读、且半年后还能读懂**的表。它的字段含义要写在文件头部，否则将来自己也要猜：

```
# run_manifest.tsv —— 本次运行的溯源清单
# 字段：key / value / source（值的来源）
key	value	source
run_id	2024-11-08T14:32:10_S1-S48	流程启动时间 + 样本范围
input_reads_sha256	3f9a...c21	sha256sum 00_raw/*.fq.gz
ref_db_kraken2	k2_standard_20240605	下载日期 + 库名
ref_db_kraken2_url	https://.../k2_standard_20240605.tar.gz	下载来源
ref_db_kraken2_md5	8c1d...	提供方公布值
tool_kraken2	2.1.3	conda list 输出
tool_samtools	1.19.2	conda list 输出
env_lock	envs/qc.lock.yaml@sha256:77ab...	锁文件内容哈希
container_kraken2	quay.io/biocontainers/kraken2@sha256:0b3e...	镜像 digest
cmd_kraken2	kraken2 --db ${KRAKEN_DB} --confidence 0.1 ...	引擎日志
```

注意 `ref_db_kraken2` 与 `tool_kraken2` **是两行**，而前者还带 URL 与校验和。这不是冗余：软件版本可以在环境里查到，数据库版本只能靠记录。

### 输出：三份交付物

| 交付物 | 形态 | 给谁 |
|---|---|---|
| 流程定义（可运行的代码） | `Snakefile` / `main.nf` + `envs/` + `config` | 要重跑的人 |
| 溯源清单 + 校验和 | `run_manifest.tsv` + `checksums.sha256` | 要核查结果的人 |
| 依赖图 + 资源用量报告 | `dag.pdf` + `trace.txt` / `report.html` | 要理解「分析怎么组织的、贵在哪」的人 |

第三份常被忽略，但它在两个场合很有用：写论文方法部分时（依赖图比一段文字更清楚），以及优化流程时（`trace` 会告诉你哪个任务吃掉了大部分内存与时间）。

### 引擎日志里应该找什么

引擎自己产出的日志是溯源素材的主要来源，但字段很多，值得知道该看哪几个：

| 来源 | 关键字段 | 用来回答什么问题 |
|---|---|---|
| Snakemake `.snakemake/log/` | 每条规则实际执行的 shell 命令 | 「当时用的参数到底是什么」 |
| Snakemake `--dag` → `dag.pdf` | 规则级依赖 | 「分析是怎么组织的」 |
| Nextflow `.nextflow.log` | 每个 task 的 hash、work 目录、命令 | 「这次跑与上次跑的差异在哪」 |
| Nextflow `trace.txt` / `report.html` | `name` / `status` / `realtime` / `peak_rss` | 「哪个任务最贵、最占内存」 |
| `batch_status.tsv` | 每个样本的 `ok` / `FAILED` / `skipped` 与耗时 | 「哪些样本要重跑」 |
| `sacct` 输出 | `MaxRSS` / `ReqMem` / `AllocCPUS` / `State` | 「下次该申请多少资源」 |

`batch_status.tsv` 的形态值得固定下来，因为它是「只重跑失败样本」这个能力的接口：

```
sample	status	seconds	note
S1	ok	182	
S3	FAILED	41	见 10_logs/S3.fastp.log
S4	skipped	0	已存在
```

`status` 三个取值就够用了，关键是**实时追加写入**：跑到一半断开时，你已经知道哪些完成了。

## 11.3 工具拼装思路（含选择决策树）

### 决策树 1：要不要上工作流引擎

```
这个流程会重复运行吗？
├─ 不会（一次性探索） → 直接写脚本。但每一步仍要落盘，为以后的固化留余地
└─ 会
      ├─ 步骤 < 5 且样本 < 10
      │     → wf_checkpoint_pipeline：手工断点骨架，够用且好懂
      └─ 步骤 ≥ 5 或样本 ≥ 10 或需要交给别人
            → wf_snakemake 或 wf_nextflow（见决策树 2）
```

### 决策树 2：引擎选型

见 11.1 的对照表。一句话版本：以文件与依赖图为中心 + 偏好 Python + 本地或单个集群 → `wf_snakemake`；需要 nf-core 生态 + 要跑在多种执行平台 → `wf_nextflow`。

两条容易被忽略的补充：**同一份流程不要两个引擎都写**（维护成本翻倍，而且两边迟早不一致）；**选型要考虑接手的人**（如果实验室全用 Nextflow，个人偏好 Snakemake 会让流程变成只有你能维护的东西）。

### 决策树 3：环境隔离的三档强度

```
你要复现的是……
├─ 「大致相同的结果」→ wf_conda_env：environment.yml 写死主次版本
│                      成本最低，但传递依赖仍会漂移
├─ 「别人能装出同一套环境」→ wf_conda_env + 锁文件（env export / conda-lock）
│                      可复现性的实际载体是锁文件里的完整依赖树与构建号
└─ 「作者当时验证过的那一套环境」→ wf_container：用镜像，并记录 digest
                       最强的手段。但记住它固定的是软件，不是数据（见坑 2）
```

三档不是互斥的：常见的组合是**容器 + 容器内仍用 conda 环境文件**，这样既能归档镜像，也能在需要时重建。

### 决策树 4：跑在哪里

```
任务规模与运行时间
├─ 单机可完成（几小时内、内存 < 64 GB） → 本地直接跑，用 --cores 控制并行度
├─ 需要大内存或长时运行
│     → wf_cluster_submit：提交到集群，按工具特性申请资源
│       ⚠ 内存申请不足会在数小时后被 OOM 杀死，损失最大
└─ 单次任务规模极大 / 需要弹性 → 容器 + 云 executor（Nextflow 在此更成熟）
```

集群上有一条硬约束要先确认：**多数 HPC 不允许 Docker**（需要守护进程与 root），必须改用 Apptainer/Singularity，或者用 `apptainer exec docker://...` 直接拉取转换。把这一点留到流程跑到一半才发现，代价很高。

### 一段完整的引擎骨架应该长什么样

```
① 结构层   wf_dag_rule
   └─ 把分析计划画成 DAG；检查有没有环与缺失步骤；
      输出 dag.pdf（审计材料）+ 可并行分组（决定最短完成时间）
② 执行层   wf_snakemake / wf_nextflow
   └─ 每条 rule / process 声明输入、输出、线程、日志、环境；
      先 dry-run 确认依赖与路径；失败后修好再跑，已完成的自动跳过
③ 恢复层   wf_checkpoint_pipeline + wf_batch_loop
   └─ 完整性判据「存在且非空」；逐样本状态表支持只重跑失败样本；
      并行度 = 总核数 ÷ 每样本线程数
④ 溯源层   wf_reproducibility + util_checksum + util_download_ref
   └─ 软件版本 + 数据库版本 + 输入校验和 + 实际命令 → run_manifest.tsv
```

### 适配器模块应该插在哪里

`wf_flexible_join` 的输入类型是 `any`，这看起来像一个万能接口，但它其实是这套系统里**最需要小心**的模块。它的设计取舍是：**接受任何输入，因此类型检查无法替代人工核对**——接入后必须显式写出实际转换逻辑与校验断言。

它正确的使用位置是「类型对不上、但语义确实需要接通」的地方，例如：

```
某工具输出的统计表 (tsv-table)
   └─→ wf_flexible_join ─→ py_pandas_io     # 转换时同时统一样本名与缺失值写法
```

而它不该被用来绕过设计问题：如果两个模块的接口对不上是因为**分析设计有矛盾**（比如要求一个还没生成的产物），那么插入适配器只是把矛盾推迟到运行期。

三个具体用途最能体现它的价值：

1. **统一样本名**（配合 `util_rename_manifest`）——这是「合并静默丢样本」的根治手段
2. **统一缺失值写法**——避免出现名叫 `-` 的分组
3. **坐标体系转换**（1-based ↔ 0-based）——配合断言校验，避免整体偏移一位

### 一条完整的示例流程：质控指标汇总与项目报告

面板里的「质控指标汇总与项目报告」预设（`preset-qc-metrics-report`，入门难度）是本章内容最短的一条端到端路径，只有 6 个节点却覆盖了本章的四件事：

```
qc_fastqc ──┐
            ├─→ qc_multi_qc ──┬─→ py_pandas_io ─→ py_export_report
qc_fastp  ──┘                 │
                              └─→ wf_reproducibility
```

| 节点 | 对应本章的哪件事 |
|---|---|
| `qc_multi_qc` | 把散落的日志汇总成项目级视图——**先有可读的中间汇总，才谈得上报告** |
| `py_pandas_io` | 解析 `multiqc_data.json` 做自定义阈值判定，而不是靠人眼看 HTML |
| `py_export_report` | 生成交付物，并在报告头部写入版本与命令 |
| `wf_reproducibility` | 把质控报告纳入溯源链，让它随结果一起归档 |

注意 `qc_multi_qc` → `wf_reproducibility` 这条边：质控报告不是「跑完就丢」的中间产物，而是**结果可追溯链上的一环**。审稿人问「你怎么知道数据质量够」时，你给出的不是回忆，而是一个带时间戳的文件。作为对比，`preset-mag-binning`（9 个节点，高阶）的资源画像完全不同：`meta_megahit` 是那条流程里唯一需要上百 GB 内存的步骤——这正是 11.4 的资源申请表要按工具特性分开估算、而不是给所有步骤一个统一值的原因。

## 11.4 关键参数取舍

### 引擎参数

| 参数 | 常用值 | 什么情况下该改 |
|---|---|---|
| `--cores` / `-j`（Snakemake） | 显式给数字 | 不给会串行执行；给的数字是**全部规则共享的上限**，规则内部的 `threads` 决定实际占用 |
| `-n` / `--dry-run` | 每次改完规则都跑 | 这是验证「依赖是否完整、路径是否正确」最便宜的方式 |
| `--use-conda` | 开启 | 这是流程可复现性的关键；不开启则所有工具共用当前环境 |
| `--rerun-incomplete` | 中断后开启 | 不加会因「文件存在但无效」而卡住 |
| `--forcerun` / `-R` | 改环境后**必须**给 | **引擎不会自动检测工具版本变化**（见坑 4） |
| `--keep-going` | 批量任务开启 | 否则一个样本失败会中断全部 |
| `--unlock` | 异常退出后 | 不解除锁时后续任何命令都报「目录被锁定」，而错误信息不够直白 |
| `--latency-wait` | 共享文件系统上调到 30~60 | NFS 上文件同步有延迟，默认 5 秒会产生「输出文件不存在」的假报错 |
| `-resume`（Nextflow） | 失败后接续 | 完全依赖 `work/` 缓存目录；手工删掉它 resume 会从头重跑 |
| `process.errorStrategy` | `'terminate'` | 集群长跑任务改 `'retry'`，用来吸收偶发的节点故障 |
| `process.maxForks` | 按集群配额设 | 不限制会一次提交数百个任务压垮集群——这是最常见的原因 |
| `-with-trace` / `-with-report` | 开启 | trace 记录每任务命令与资源峰值，report 是可视化版本；两者都是溯源材料 |

### 可重复性记录的参数

| 参数 | 常用值 | 什么情况下该改 |
|---|---|---|
| 校验和算法 | `sha256` | 提供方只公布 md5 时按提供方的来；核对的意义在于与**公布值**比对，而不是自己算一个 |
| 哈希对象 | **单个文件**各一条 | 记录单文件哈希比汇总哈希有用：能定位具体哪个文件变了 |
| 记录时机 | **每次运行**都生成 | 只做一次就无法区分「同一份数据跑了两次」与「数据换了但没人注意」 |
| 版本粒度 | 完整版本号 | `samtools --version` 会连带列出 htslib 版本，应完整记录而不是只取第一行数字 |
| 数据库版本标识 | 固定发布版本 + 下载日期 | **不要用 latest**：提供方会在同名文件下更新内容 |
| 参考基因组版本 | 与结果一并记录 | 同一物种不同版本的参考有数万个位点差异，比对与变异结果都会变 |
| 校验和入库 | 校验和进版本库，数据不进 | 校验和列表体积极小，应当随代码提交 |

### 环境与容器参数

| 参数 | 常用值 | 什么情况下该改 |
|---|---|---|
| `channel_priority` | `strict` | 避免跨通道混用导致的依赖冲突；代价是有时求解失败，此时需显式指定通道 |
| 通道顺序 | bioconda → conda-forge → defaults | 顺序写错会装到不同来源的同名包，问题在运行期才暴露 |
| 版本指定粒度 | 精确（`fastp=0.23.4`） | 不指定版本等于放弃可复现性；pip 补装会破坏依赖一致性，尽量避免 |
| `env export --no-builds` | 含 build 号最严格 | `--no-builds` 可移植性更好但略宽松；跨平台重建时用 |
| 环境位置 | 项目内 `-p envs/<name>` | 用路径而非名字，避免不同项目都叫 `bioinfo` 而误用别人的环境 |
| 镜像引用 | **digest**（`@sha256:...`） | tag 是可变的，上游重建同一个 tag 会得到不同内容；`latest` 等于放弃版本固定 |
| `docker --user` | `$(id -u):$(id -g)` | 容器内以 root 运行会生成 root 所有的输出文件，宿主机上无法修改 |
| `--writable-tmpfs`（Apptainer） | 需要写临时文件时开 | Apptainer 默认只读，很多工具会往 `/tmp` 写 |
| 镜像基础层 | `condaforge/miniforge` | 可与 conda 环境文件衔接；用 `ubuntu` 基础层需手工装依赖 |

### 集群资源申请

| 参数 | 常用值 | 什么情况下该改 |
|---|---|---|
| `--cpus-per-task` | **必须与工具实际线程数一致** | 申请 16 核但命令里没传 `-t $SLURM_CPUS_PER_TASK`，实际单线程运行——这是最常见的浪费 |
| `--mem` | 按工具特性估算 | `fastp` 几 GB；**宏基因组组装常需 100~250 GB**。申请不足会在数小时后被 OOM 杀死 |
| `--time` | 比预期长一些 | 超时会被强制杀死；但设得过长会降低排队优先级 |
| `--array=1-N%M` | `%M` 限制并发元素数 | 不限制会一次占满队列，影响所有人 |
| `--output` / `--error` | **必须显式指定**到项目日志目录 | 不指定则作业输出散落在提交目录，批量时几十个 `slurm-*.out` 无法与样本对应 |
| `--dependency=afterok:<jobid>` | 串起多步 | 比 `sleep` 轮询好：轮询过频会占满登录节点或被限制 |
| `--mail-type` | `FAIL` | 只在失败时通知，避免几百封邮件 |
| `sacct` 查询 | 每个作业结束后必看 | **这是调整下次申请值的唯一依据**（见坑 5） |

### 批量与并行

| 参数 | 常用值 | 什么情况下该改 |
|---|---|---|
| `set -e` | **批量循环里不要用** | 第一个样本失败会中断整批；改用显式 `if` 判断并记录状态 |
| `xargs -P` / `parallel --jobs` | **总核数 ÷ 每样本线程数** | 写成 `--jobs 16` 而每个任务内部又开 `-w 8`，实际申请 128 线程，比串行还慢 |
| `--joblog` | 开启 | 记录每个任务的退出码与耗时，是「只重跑失败样本」的依据 |
| `--halt now,fail=1` | 视情况 | 开启则任一失败立即终止其余；不开启时失败会被淹没在几百行输出里 |
| `while read` 的 `IFS` | `IFS=$'\t'` | 读 TSV 必须指定，否则含空格的字段被拆开导致样本名错位 |
| 日志粒度 | **每样本一个日志文件** | 所有样本写同一个文件时，并发输出互相穿插，无法排查单个样本 |
| 内存配额 | 每任务峰值内存 × 并发数 | 并发任务共享内存；超配会被 OOM 杀掉其中几个，且看不出原因 |

## 11.5 常见坑

### 坑 1：只记软件版本，不记数据库版本

这是生信复现失败**最常见的单一原因**。它的危险之处在于「感觉已经做得很规范了」——环境锁文件写了、`--version` 记了、容器也用了，但注释与分类用的数据库版本没记。

需要记录数据库版本的模块类型包括但不限于：`meta_kraken2`、`meta_bracken`、`meta_metaphlan`、`meta_humann` 类的功能注释、`tax_gtdbtk`、`anno_bakta`、`res_card_rgi`、`res_vfdb`、`phage_genomad`、`amplicon_taxonomy_assign`、`phy_its_phylogeny`。凡是结果里出现「物种名」「功能名」「耐药基因名」的步骤，都在这个名单上。

记录的内容要包含四项：**库名 + 版本/日期 + 来源 URL + 提供方公布的校验和**。

```
ref_db_gtdbtk	R220	GTDB 发布版本号
ref_db_gtdbtk_url	https://data.gtdb.ecogenomic.org/releases/release220/...	来源
ref_db_gtdbtk_md5	<提供方公布值>	用于确认下载正确
ref_db_gtdbtk_date	2025-01-14	下载日期（同一版本号也可能被重新打包）
```

`util_download_ref` 提供了把这四项一起落盘的写法。关键在于**不要用 `latest`**：提供方会在同名文件下更新内容，一年后的重跑会得到不同的结果，而你不会有任何察觉。

### 坑 2：容器固定的是软件，不是数据

这是容器化**最容易被忽略的缺口**。用了容器之后很容易产生一种「环境已经完全固定了」的安全感，但下面这些都不在镜像里：

- **参考数据库**：Kraken 2 的索引库、GTDB 的比对库、CARD/VFDB 的序列库
- **索引文件**：bowtie2/BWA/minimap2 的索引、DIAMOND 的 `.dmnd`、HMMER 的 `.h3m`
- **分类模型**：各种需要训练的模型权重
- **参考基因组**：宿主基因组、参考菌株基因组

它们不在镜像里的原因很简单：体积太大（几十到几百 GB）。于是「容器 + 数据版本管理」是**两条并行的主线，缺一不可**。

一条具体的验证方法：把流程在同一个 digest 的镜像上跑两次，但中间替换一次参考数据库。如果两次结果不同而你事先没记录数据库版本，你就复现了坑 1 的全部症状——而容器一点忙都帮不上。关于容器还有两个具体的坑：**在流程里写 `latest` 标签**（等于放弃版本固定）；**容器里以 root 运行**（输出文件属主变成 root，宿主机上后续步骤无法写入或删除，用 `--user $(id -u):$(id -g)` 避免）。

### 坑 3：断点判据用「文件存在」而不是「存在且非空」

```bash
if [ -f "$output" ]; then echo "跳过"; fi   # 错：被中断的任务常留下 0 字节文件
if [ -s "$output" ]; then echo "跳过"; fi   # 对：存在且非空
```

这个坑的代价被严重低估了：**它产生的错误信息离真正的原因很远**。被中断的任务留下一个 0 字节的 `contigs.fasta`，下游把它当有效输入，组装统计得到 0 条 contig，或者工具报一个与「文件为空」毫无关系的解析错误。你会去查工具参数、查数据质量，而不是查那个文件的大小。

正确的完整性判据是分层的：

| 判据 | 成本 | 能拦住什么 |
|---|---|---|
| 文件存在 | 极低 | 什么都没拦住 |
| **存在且大小 > 0** | 极低 | 被中断留下的 0 字节文件 |
| 内容可解析（如行数 > 0、FASTA 可读） | 低 | 部分写入的文件 |
| 校验和匹配预期 | 中 | 文件被替换或损坏 |

Bash 里用 `[ -s "$f" ]`，Python 里用 `output.exists() and output.stat().st_size > 0`。`wf_checkpoint_pipeline` 的示例骨架里用的就是这个判据，可以直接抄。同理，Snakemake 的 `--rerun-incomplete` 就是为这一类情况准备的：不加它，引擎会因为「文件存在」而认为该步骤已完成。

### 坑 4：引擎不会自动检测工具版本变化

这条需要单独写出来，因为很多人的直觉是反的。Snakemake 依据**文件时间戳与内容**判断是否需要重跑，Nextflow 依据**脚本哈希**判断——两者都**不检测外部工具或环境的变化**。你把 `envs/qc.yaml` 里的 `fastp=0.23.4` 改成 `0.24.0`，输入文件没变、旧的输出文件还在，引擎就认为「输出比输入新，不需要重跑」。于是你得到了一份**标注着新环境、实际是旧环境产出的结果**。

这不是引擎的缺陷，而是设计取舍：检测工具版本变化需要每次运行都枚举全部依赖的版本，成本太高。**正确做法是把它变成一个显式决策**：

```bash
# 改了某个工具版本后，强制重跑受影响的规则及其下游
snakemake --cores 16 --use-conda --forcerun qc_fastp
# Nextflow 侧：-resume 会因 script 内容变化而重跑该 process，
# 但环境（容器 digest、conda 环境）变化同样不会被自动感知，需换 -work-dir 或清理缓存
```

并且在 `run_manifest.tsv` 里记录**这次运行实际重跑了哪些步骤**。否则半年后你无法区分「这份结果是新版工具跑的」还是「标签换了但结果没重跑」。

### 坑 5：集群资源申请——OOM、多核浪费与 sacct

集群资源申请需要经验判断，但有三条可以立刻用上的规则。

**① 内存申请不足会在数小时后被 OOM 杀死，损失最大。** 生信工具的内存需求差异极大：

| 工具类型 | 内存量级 |
|---|---|
| `fastp`、`seqkit`、大部分质控工具 | 几 GB |
| 单菌基因组组装（SPAdes） | 十几到几十 GB |
| **宏基因组组装（MEGAHIT / metaSPAdes）** | **100~250 GB** |
| 大规模分类（Kraken 2 + 大库） | 库大小 + 工作内存，常需 64 GB 以上 |

OOM kill 的特点是**发生在运行数小时之后**，而且日志里往往没有明确的内存信息，只有一个突然中断。第一次跑某类任务时**宁可略宽**，看到实际用量后再收紧。

**② 申请了多核但工具没用上，是常见浪费。**

```bash
#SBATCH --cpus-per-task=32
spades.py --careful -1 R1.fq.gz -2 R2.fq.gz -o out    # ← 没有 -t，实际单线程
spades.py --careful -t "$SLURM_CPUS_PER_TASK" -1 R1.fq.gz -2 R2.fq.gz -o out   # 正确
```

代价不只是自己的配额——它占用集群资源、延长所有人的排队时间。

**③ `sacct` 的实际用量是调整下次申请值的依据。**

```bash
sacct -j <jobid> --format=JobID,JobName,Elapsed,MaxRSS,ReqMem,AllocCPUS,State
```

看两个比值：`MaxRSS / ReqMem` 远小于 1 说明内存申请过多（白白增加排队时间），接近 1 且 `State` 是 `OUT_OF_MEMORY` 说明申请不足；`AllocCPUS` 很大而任务其实是单线程工具，就是明显的浪费。实测中经常看到「申请 64 核实际只用 4 核」「内存申请是实际用量的五倍」——**别凭感觉猜，看 sacct。**

### 坑 6：并行度超配

```bash
# 16 个样本并行 × 每个 8 线程 = 128 线程，而机器只有 32 核
parallel --jobs 16 'fastp ... -w 8' ::: $(cat samples.txt)
```

结果是大量时间花在上下文切换与内存争抢上，**整体比串行还慢**，而且日志看不出原因。正确的算法只有一条：`样本并行数 × 每样本线程数 ≤ 总核数`。写成代码，不要手算：

```bash
TOTAL_CORES=$(nproc)
PER_SAMPLE_THREADS=4
JOBS=$(( TOTAL_CORES / PER_SAMPLE_THREADS ))
[ "$JOBS" -lt 1 ] && JOBS=1
echo "并行 $JOBS 个样本 × 每个 $PER_SAMPLE_THREADS 线程 = $((JOBS * PER_SAMPLE_THREADS)) 核"
```

内存同理：并发数 × 单任务峰值内存不能超过可用内存，否则会被 OOM 随机杀掉其中几个，而你只会看到「结果少了几个样本」。

### 坑 7：静默的接口与格式错误

流程层面有一类错误不会让引擎报错，只会让结果错：**上游产出的格式与下游期待的格式差一点点**。

| 现象 | 真正的原因 | 检查方法 |
|---|---|---|
| 下游结果为空但流程「成功」 | `seqkit grep` 忘了 `-n`，按序列内容而不是序列名匹配 | 手工跑一次 grep，看命中的序列数 |
| 表里所有数据挤在一列 | 某一步用空格而不是制表符输出（`awk` 没设 `OFS`） | 用 `awk -F'\t' '{print NF}'` 看列数 |
| 样本数变少了 | 合并用了 `inner`，或样本名大小写/下划线不一致 | 集合差集 + 行数断言 |
| 所有区间偏移一位 | GFF（1-based）当作 BED（0-based）用了 | 断言区间长度与原始记录一致 |
| 覆盖度虚高 | `samtools depth` 没加 `-a`，分母是覆盖位置数而不是基因组长度 | 对比 `-a` 与不加时的平均值 |
| 交换文件后数值全错 | 文本文件经 Windows 传输后行尾变 CRLF，或小数分隔符随区域设置变化 | 统一用 `write_csv`/`write_excel_csv`，避免 base R 的 `write.csv` |

共同的解法是**在模块入口做显式校验**，而 `wf_flexible_join` 与 `util_args_validate` 提供了现成的写法。核心思想是：一条连线「能连上」只说明类型兼容，**不说明内容正确**。类型检查能拦下跨越数据结构（表 ↔ 树）的错误，但拦不下「分隔符写错了」这类同类型内的错误。

### 坑 8：手工操作破坏了续跑能力

自动化流程最脆弱的环节往往是人的手：**手工删除中间文件来「清理空间」**（续跑全部失效，而且要到下一次运行才发现）；**手工删除 Nextflow 的 `work/`**（`-resume` 完全依赖它，清理磁盘应用 `nextflow clean -f -k`）；**手工修改中间结果**（改过之后结果与代码不再一致，每一步都不可信）；**在登录节点上跑重计算任务**（会影响所有用户，管理员通常直接杀掉）；**不查 `sacct` 就直接重跑**（如果失败原因是内存不足或数据问题，重跑会再次失败）。

一个实用的防御：把「清理」也写成脚本并纳入流程，而不是在终端里敲 `rm`。这样「清理了什么」至少留下了记录。

### 坑 9：只在交互式会话里跑通过

「我这儿能跑」是流程不可复现的经典前兆。交互式会话里跑通、写进脚本就失败，原因通常是三件事之一：① **依赖了交互式 shell 的初始化**——`conda activate` 在非交互式脚本里会因未初始化而报 `CommandNotFoundError`，脚本里必须显式 `eval "$(conda shell.bash hook)"` 或直接调用环境的绝对路径；② **依赖了当前工作目录**——相对路径换个目录就找不到文件，绝对路径又不可移植，正解是用相对于项目根的路径并在开头 `cd` 到项目根；③ **依赖了手工设置的环境变量**，这类依赖在脚本里根本不存在。

**验证方法：在一个干净目录、用一份新克隆的代码、按 README 的步骤重跑一遍。** 成本一小时，收益是知道流程到底能不能被别人用。

### 坑 10：作业数组与样本清单错位

```bash
#SBATCH --array=1-48
SAMPLE=$(sed -n "${SLURM_ARRAY_TASK_ID}p" 10_logs/sample_list.txt)
```

这段写法本身没问题，但有一个隐藏的耦合：**作业数组的编号依赖样本清单的行号**。运行期间任何人往清单里增删一行，编号与样本的对应关系就整体错位——一部分样本被跳过，一部分被重复处理，两者都不会报错。它危险的地方在于**在时间上分散**：提交作业、修改清单、作业执行发生在不同时刻，出错时没有人会把它们联系起来。

三种修法，按可靠程度排序：

| 做法 | 说明 |
|---|---|
| **用样本名而不是行号做索引** | 作业数组每个元素带一个固定的样本名，并把清单的哈希记进 `run_manifest.tsv` |
| **提交时冻结清单** | 复制成 `10_logs/sample_list.<run_id>.txt`，作业只读这个快照 |
| **限制并发并加前置校验** | `--array=1-48%8` 控制同时运行数；脚本开头核对清单行数与数组范围，不一致就直接失败 |

同样的道理适用于任何「用序号索引文件」的写法：`for i in $(seq 1 48)`、`xargs -n1` 配合 `sed -n "${i}p"`、按字母序遍历目录并与另一份清单按位置对齐——都属于同一类风险。**能用键（样本名）对齐的地方，就不要用位置对齐。** 这条原则与第 10 章里「进入 limma/DESeq2 前必须 `identical()` 校验顺序」是同一条。

### 交付前自检清单

```
[ ] 流程能在新建的目录里按 README 从头跑通（不是「在我机器上能跑」）
[ ] 每条规则都声明了完整的 output（没有「实际产三个文件只声明一个」）
[ ] 每条规则都声明了 log，并用 2> {log} 把 stderr 写进去
[ ] 断点判据是「文件存在且非空」，不是「文件存在」
[ ] 环境用锁文件固定；容器用 digest 而不是 tag
[ ] 参考数据库的版本、来源 URL、校验和、下载日期都记进了 run_manifest.tsv
[ ] 输入数据的 sha256 校验和已生成，且是本次运行生成的
[ ] run_manifest.tsv 带表头与字段说明，能独立读懂
[ ] 改了工具版本后已用 --forcerun 显式重跑，并在清单里记录了重跑范围
[ ] 集群作业显式指定了 --output/--error，日志能按样本对应
[ ] 集群资源申请与工具实际线程数一致；已用 sacct 核对过实际用量
[ ] 并行度满足「样本并行数 × 每样本线程数 ≤ 总核数」
[ ] 依赖图（dag.pdf）与实际流程一致，且是从流程定义导出的而不是手画的
[ ] 失败样本有独立的状态记录，支持只重跑失败样本
```

## 11.6 与面板模块 id 的对应

这一层在面板里对应 29 个模块，横跨三个分类：流程引擎与调度、工具与数据操作、数据格式与互转。

### 流程引擎与调度（`workflow`，layer = engine）

| 模块 id | 一句话说明 |
|---|---|
| `wf_snakemake` | 声明式 rule + 依赖图编排可重跑流程，支持逐规则环境隔离与集群 profile |
| `wf_nextflow` | 数据流式 DSL 编排跨平台流程，与容器及 nf-core 生态集成最成熟 |

| `wf_reproducibility` | 生成溯源清单：软件版本 + 数据库版本 + 输入校验和 + 实际命令 |

| `wf_cluster_submit` | 集群提交与资源申请（Slurm/PBS），并提供回收 sacct 用量的写法 |

| 模块 id | 一句话说明 |

| `util_seqkit` | FASTA/FASTQ 的读写、过滤、统计与拆分；注意 `grep -n` 与 `-w 0` |
| `util_samtools` | SAM/BAM/CRAM 的查看、排序、取子集与统计；`-f`/`-F` 含义相反 |

### 数据格式与互转（`io-formats`，layer = engine）

| 模块 id | 一句话说明 |
