# 错误与故障排查

本文件的组织方式与其它参考文档不同：**它按「问题现象」索引，不按工具索引。**

原因很直接——遇到问题时，你手上只有现象。「结果里一个物种都没有」「作业跑到第五个小时被杀了」「这张图缩到单栏就看不清」——你几乎不会先知道是哪个工具造成的。因此这里的每一节都是一个现象类别，每条条目都按同一结构写：

**现象 → 可能原因 → 怎么确认 → 怎么修**

确认步骤都写了**具体命令或检查点**，而不是「检查一下参数」。如果某条与你的情况不符，请把它当作「先排除这一项」而不是「一定是这个原因」。

> 关于版本：下面的命令示例不标注工具版本。工具的具体行为随版本变化，**以你所用版本的官方文档为准**；模块条目里的 `provides.version` 只是这个知识系统验证过的版本区间。

## 1. 结果为空或几乎无结果

### 1.1 过滤命令跑完了，但输出文件是空的

- **现象**：`seqkit grep`、`grep`、`awk` 之类的过滤命令退出码为 0，输出文件 0 字节或只有表头。
- **可能原因**：`seqkit grep` 默认按**序列内容**匹配，而不是按序列名匹配。忘了 `-n` 时它去找一条内容等于你那个 id 的序列，当然找不到。这是「结果为空」最常见的原因。
- **怎么确认**：不加输出重定向，直接跑一遍看命中数；或先在原文里 `grep -c "你的id"` 确认这个 id 真的存在，以及它的写法（`>` 后面常带描述段，如 `>seq1 length=150`）。
- **怎么修**：加 `-n`（按名字匹配）或 `-p`（正则匹配），并顺手确认 id 的大小写、版本后缀（`.1`）与描述段。过滤后立刻 `seqkit stats` 看条数是否符合预期。

### 1.2 比对率极低，几乎没有读长比对上去

- **现象**：短读长或长读长的比对率只有个位数百分比，覆盖度为 0。
- **可能原因**：**用错了平台预设**。把 Nanopore 长读长用 `map-ont` 之外的预设比对（或干脆用短读长比对器），会比出很低的比对率；反过来，把短读长当长读长处理也一样。第二种常见原因是参考序列与样本不是同一个物种/菌株，或参考序列的版本不对。
- **怎么确认**：先确认读长长度分布（`seqkit stats -a`），再确认参考序列的物种与版本。快速判断：把同一批读长比到宿主基因组上，如果比对率很高，说明比对器参数没问题，是参考选错了。
- **怎么修**：长读长用 `minimap2 -ax map-ont`（ONT）或 `-ax map-pb` / `map-hifi`（PacBio）；短读长用 BWA/Bowtie2。参考基因组的来源与版本必须与结果一并记录（见第 6 节）。

### 1.3 去宿主之后什么都没剩下

- **现象**：去宿主步骤的输出读长数接近 0，或比预期低一个数量级。
- **可能原因**：两种情况，方向相反。① 宿主参考基因组选错了（例如把细菌基因组当成宿主）——那就会把所有东西都当成「宿主」去掉；② 宿主比例确实很高（临床/组织样本常见 90% 以上），此时剩下 5% 是正常的。
- **怎么确认**：看去宿主步骤自己输出的统计（`samtools flagstat` 或模块产出的 host_stats）。**判断标准是去宿主前后的分类结果对比，而不是感觉**：去宿主前跑一次 `qc_contamination_screen`（Kraken 2），去宿主后再跑一次，看宿主占比是否降到可接受范围。
- **怎么修**：若宿主占比没有明显下降，说明参考不对或比对参数太松；若宿主占比正常但剩余数据太少，那是实验设计问题，需要增加测序量或改富集方法，不是调参数能解决的。

### 1.4 分类结果里大量 `unclassified`

- **现象**：Kraken 2 / MetaPhlAn 的结果里 unclassified 比例达到 50% 以上。
- **可能原因**：**这不一定是数据问题。** 环境样本、病毒组、或含大量新物种的样本，unclassified 高是正常的——数据库里没有近缘基因组可匹配。真正需要担心的是「应该有结果却都是 unclassified」，那通常是数据库没配好或 `--confidence` 设得过高。
- **怎么确认**：看 unclassified 与已分类部分的物种组成是否合理；把 `--confidence` 从默认值（0.0）调回默认再跑一次对比。如果调低后出现大量「跨界的奇怪物种」，说明是噪声被放出来了；如果调低后出现的是合理的近缘属，说明原本阈值太高。
- **怎么修**：环境样本用包含更多基因组的库（如 plusPF）；病毒组用专门的病毒库；同时记录**库名与版本**（见第 6 节）。不要靠调 `--confidence` 去「产生」结果。

### 1.5 差异分析结果一个显著基因都没有

- **现象**：`padj` 全部大于 0.05，或 `padj` 全为 `NA`。
- **可能原因**：① 多重校正用了控制 FWER 的方法（`multipletests` 的默认 `'hs'`）——在几千次比较时几乎不会有显著结果；② `topTable` 忘了 `number = Inf`，只对前 10 个特征做了校正；③ 低表达特征没有过滤，拖累了校正；④ 数据里真的没有信号（见 4.2）。
- **怎么确认**：先查校正方法与校正范围，再画 p 值直方图。如果 p 值接近均匀分布，说明确实没有信号，不是流程问题。
- **怎么修**：校正方法改成 `fdr_bh`；`topTable` 加 `number = Inf`；先按「至少在最小分组规模个样本中达到阈值」过滤低表达特征，再重跑。**校正必须对全部检验的 p 值一次性进行**，按物种或基因分批校正会让每一批都有人为的显著结果。

### 1.6 程序退出码是 0，但产物文件不存在

- **现象**：命令「成功」了，但下一步找不到输入文件，或找到的是 0 字节文件。
- **可能原因**：① 工具把输出写到了别处（默认输出目录、当前工作目录），而你指定的是相对路径；② 命令实际失败但被管道吞掉了退出码（`cmd | tee log` 的退出码来自 `tee`）；③ 被中断的任务留下了 0 字节文件。
- **怎么确认**：`ls -l` 看文件是否存在与大小；`set -o pipefail` 后重跑看真实退出码；看工具的日志而不是只看终端最后一行。
- **怎么修**：所有产物路径显式写出；管道命令加 `set -o pipefail`；**完整性判据用「存在且非空」，而不是「存在」**（见第 6 节 6.3）。

### 1.7 某一步的中间产物是空的，但上游日志显示正常

- **现象**：上游工具报告处理了 N 条记录，下游拿到的文件却是空的。
- **可能原因**：① 输出被重定向到了同一个文件（`cmd > f` 里 `f` 同时也是输入）；② 中间文件被并发任务互相覆盖（多个样本写同一个文件名）；③ 磁盘写满。
- **怎么确认**：`df -h` 看磁盘；检查并发任务的输出路径是否含样本名；检查是否有文件名冲突（不同样本展开成同一路径）。
- **怎么修**：所有中间产物路径**必须包含样本标识**；并发任务各写独立日志文件；磁盘空间纳入流程开头的检查项（`util_args_validate` 的检查项之一）。

### 1.8 物种/功能表里所有值都是 0

- **现象**：丰度矩阵读进来了，形状也对，但所有数值都是 0。
- **可能原因**：① 归一化步骤把整数计数做了整除（整数数组做除法会截断，小于 1 的值全变 0，且不报错）；② 转置方向搞错，把特征数当成了样本数；③ 合并时列名对不上，`fillna(0)` 把所有内容填成了 0。
- **怎么确认**：看上游文件的原始数值（`head` 直接看文本）；检查矩阵形状是否符合「特征数 × 样本数」的预期；检查 `dtype` 是 `int` 还是 `float`。
- **怎么修**：任何除法前先 `astype(float)`；合并后立刻断言总和非 0 且与上游一致；`fillna(0)` 只用在计数数据上，log 变换后的数据填 0 表示的是「最小值」而不是缺失。

## 2. 内存不足 / 进程被杀

### 2.1 作业跑到几小时后突然消失，日志没有明确错误

- **现象**：`State` 是 `OUT_OF_MEMORY` 或 `CANCELLED`，或者本地运行时进程无提示消失。
- **可能原因**：**内存申请不足被 OOM killer 杀死。** 生信工具的内存需求差异极大：`fastp`、`seqkit` 这类流式工具只要几 GB；单菌基因组组装（SPAdes）要十几到几十 GB；**宏基因组组装（MEGAHIT/metaSPAdes）常需 100~250 GB**；大库的 Kraken 2 分类需要「库大小 + 工作内存」。OOM 的特点是**发生在运行数小时之后**，损失最大。
- **怎么确认**：查 `sacct -j <jobid> --format=JobID,JobName,State,MaxRSS,ReqMem`；本地运行时用 `/usr/bin/time -v cmd` 看 `Maximum resident set size`；`dmesg | grep -i "killed process"` 也能看到 OOM killer 的记录。
- **怎么修**：按工具特性估算初始值并**宁可略宽**，看到实际用量后再收紧。把 `MaxRSS` 与 `ReqMem` 对比：远小于 1 说明申请过多（白白增加排队时间）。也可以降低单次处理的数据量（先抽样跑通，再全量跑）。

### 2.2 同时跑多个样本时机器卡死或部分任务被杀

- **现象**：并行处理一批样本，中间几个任务失败，其余成功；或整机响应极慢。
- **可能原因**：**内存超配。** 并发数 × 单任务峰值内存超过了可用内存，内核随机杀掉其中几个。任务本身没有 bug，只是同时跑的太多了。
- **怎么确认**：把并发数降到 1，逐个跑一遍——如果全部成功，就确认是内存超配。用 `/usr/bin/time -v` 测单任务峰值内存，再乘以并发数。
- **怎么修**：按 `可用内存 ÷ 单任务峰值内存` 计算并发数，并留 20% 余量。不要靠「上次侥幸跑通了」来决定并发度——那只是因为当时恰好没有别的任务在跑。

### 2.3 读长比对的覆盖度计算崩溃或极慢

- **现象**：`samtools mpileup`、`bedtools genomecov` 在处理高覆盖度数据时内存暴涨。
- **可能原因**：高覆盖度的扩增子或质粒数据会让深度计算的中间结构变得非常大。`samtools mpileup` 的默认最大深度是 8000，超过的部分会被**静默降采样**——它既浪费时间又不给出正确的高深度值。
- **怎么确认**：先看平均深度（`samtools depth | awk '{s+=$3} END {print s/NR}'`）。如果平均深度远超 8000，就是这个问题。
- **怎么修**：明确知道自己在做什么时显式调高 `-d`；但更常见的正确做法是**先降采样或去重**，而不是把深度阈值调到几十万——那种覆盖度下的碱基质量通常不足以支撑变异结论。

### 2.4 R 会话在读取或合并大表时被系统杀掉

- **现象**：`read_tsv` 或 `left_join` 处理百万行表时 R 进程被杀。
- **可能原因**：R 的数据框在内存中是整体复制的，`join`、`pivot_longer` 这类操作会产生多个副本，峰值内存可能是表本身的数倍。而 **R 没有 NumPy 那样紧凑的数值存储**——字符列尤其占内存。
- **怎么确认**：`object.size(df)` 看对象大小；`gc()` 看当前占用；用 `pryr::object_size()` 或者干脆转到命令行侧看进程 RSS。
- **怎么修**：读入时用 `col_types` 只读需要的列；把字符列转成 factor；分成几批处理后合并结果；表特别大时改用 `data.table`，或先落盘成 Parquet 后在 Python 侧用 `py_numpy_arrays` / `io_interop_standard` 处理。

### 2.5 距离矩阵或聚类在样本数上千时爆内存

- **现象**：样本数超过一两千时，`dist()` 或 `pdist()` 报内存错误。
- **可能原因**：成对距离矩阵是 `O(n²)` 的。2000 个样本的稠密距离矩阵约 32 MB（双精度），10000 个样本约 800 MB——还没算中间副本。而很多算法（如层次聚类）还需要额外的 `O(n²)` 结构。
- **怎么确认**：算一下 `n² × 8 字节`；用 `object.size()`（R）或 `matrix.nbytes`（NumPy）核对。
- **怎么修**：不需要完整矩阵时用 `pdist` 的距离向量形式；样本量太大时改用基于近邻的方法，或先做特征筛选/降维再算距离。**不要把完整距离矩阵写成 CSV**——文本形式会比二进制大一个数量级。

## 3. 连不上的数据流（接口与格式对不上）

### 3.1 面板上连线是红的，中间插了转换模块还是红的

- **现象**：两个模块之间插入了转换模块，连线仍然判定为不匹配。
- **可能原因**：连线的合法性判定依据是 `type`（进而归到 `shape`），不看名字。`shape` 只有 `any` / `sequence` / `sequence-set` / `table` / `alignment` / `tree` / `figure` / `list` / `code` 几种。**跨 shape 的连线（例如 `table` → `tree`）必须插入一个真正改变了数据结构的模块**，而不是一个只改格式的模块。
- **怎么确认**：在面板里看两端模块的输入输出端口类型；对照 `data/catalog.json` 的 `dataTypes[].shape`。
- **怎么修**：找 `io_*` 分类下真正做结构转换的模块（如 `io_newick_convert`、`io_table_to_phylip`）；如果确实不存在合适的转换，说明**分析设计有缺口**，应该补一个步骤而不是硬接。

### 3.2 表能连上，但下游报「列不存在」或「解析失败」

- **现象**：类型检查通过（绿线或黄线），程序运行时却说找不到某列或无法解析。
- **可能原因**：类型兼容只保证「都是表格」，**不保证分隔符、列名、首行是表头**这些细节一致。典型情况：上游输出是空格分隔，下游按制表符解析；上游有注释行；上游首列是行号而不是 id。
- **怎么确认**：`head -2 file | cat -A` 看真实的分隔符与行尾（`^I` 是制表符，`^M$` 是 CRLF）；`awk -F'\t' '{print NF}' file | sort -u` 看每一行的列数是否一致。
- **怎么修**：在两者之间插入 `wf_flexible_join` 做显式转换，并**写出校验断言**（列数、行数、id 唯一性）。这个模块的输入类型是 `any`，所以任何连线都不会报类型错误——它的正确性完全依赖你写的校验。

### 3.3 合并之后样本数变少了

- **现象**：两个表按样本合并，结果少了样本，但没有任何报错。
- **可能原因**：① 用了 `inner` 连接，键不匹配的行被静默丢掉；② 样本名不一致——大小写、连字符 vs 下划线、前后空格、`.fq.gz` 后缀，任何一处不同都会被当成不同样本；③ 连接键的**类型**不一致（一边是字符 `"1"`，一边是数值 `1`）。
- **怎么确认**：做集合差集并**打印出来**，而不是只判断是否为空：
  ```python
  missing = set(left["sample"]) - set(right["sample"])
  print(sorted(missing)[:20])
  ```
  pandas 用 `merge(validate="many_to_one")` 让键重复主动报错；dplyr 用 `anti_join` 查未匹配项；连接键类型不一致时 dplyr 会给出提示（`joining by different types`），要认真看。
- **怎么修**：整理阶段用 `left` 保留主表全部行；**每次 merge 后立刻断言行数符合预期**（`inner` 之后行数变少、`left` 之后 NaN 变多，都是键不匹配的信号）。根治办法是用 `util_rename_manifest` 统一命名规范，从源头消除不一致。

### 3.4 行数与预期一致，但数值全错位

- **现象**：合并成功，行数也对，但某些样本的数值明显不对。
- **可能原因**：**按位置对齐而不是按键对齐。** R 的 `dist`、`hclust`、limma、DESeq2 都按位置匹配，`cbind`/`merge` 之外的操作尤其如此。样本名顺序不同、或某一侧多了一个样本，整体就会错位一格——而形状看起来完全正常。
- **怎么确认**：在进入这些函数前打印两侧的标识：
  ```r
  stopifnot(identical(colnames(expr), meta$sample))
  ```
  Python 侧：`assert (counts.columns == meta.index).all()`。
- **怎么修**：**每一次进入按位置对齐的函数前都加一条断言。** 这不是可选的检查，而是唯一能发现这类错误的手段。另外，能用样本名做键的地方就不要用位置索引。

### 3.5 GFF→BED 之后所有区间偏移一位

- **现象**：区间看起来「差不多对」，但边界总是差一个碱基，下游取序列得到的蛋白起始处不对。
- **可能原因**：**坐标体系混淆。** GFF/GTF/GenBank/VCF 是 1-based 闭区间；BED 是 0-based 半开区间；Biopython 内部是 0-based 半开区间。转换必须显式加减 1。
- **怎么确认**：取一个已知基因转换前后对比长度：GFF 的 `end - start + 1` 应等于 BED 的 `end - start`。
- **怎么修**：转换代码里写断言，不要靠注释提醒：
  ```python
  assert ((bed["end"] - bed["start0"]) == (gff["end"] - gff["start"] + 1)).all()
  ```
  用 `io_gff_convert` 或 `py_biopython` 里现成的写法，不要自己用 `awk` 手算。

### 3.6 注释转换后下游定量结果全是 0

- **现象**：注释文件转换成功了，但定量工具报告「没有可用的 feature」或结果全 0。
- **可能原因**：转换时只保留了 `gene`/`CDS` 层级，丢掉了 `exon`。不少定量工具按 exon 统计，缺少 exon 就会统计为 0。另一个原因是 CDS 的 `phase` 字段或 `partial` 标记被丢弃。
- **怎么确认**：`grep -c -P "\texon\t" converted.gff` 与原始文件对比；检查转换日志里报告的各 feature 类型计数。
- **怎么修**：转换时保留完整的 feature 层级（不要只挑 gene/mRNA/CDS），并保留 `phase` 与 partial 标记。转换后**逐一核对关键属性**，而不是只看行数。

### 3.7 树文件往返转换后支持度或枝长消失

- **现象**：Newick → Nexus → Newick 之后，分支上的 bootstrap 值不见了，或枝长全变成 0。
- **可能原因**：部分转换器只保留拓扑。内部节点标签（支持度常写在这里）、枝长、Nexus 的定根标记 `[&R]`/`[&U]`、`translate` 块都可能被丢弃。**丢支持度不会报错**，你只会在画图时发现分支上什么都没有。
- **怎么确认**：比较转换前后文件的叶节点数、内部节点标签数、枝长范围：
  ```r
  t1 <- read.tree("before.nwk"); t2 <- read.tree("after.nwk")
  cat(length(t1$tip.label), length(t2$tip.label), "\n")
  cat(length(t1$node.label), length(t2$node.label), "\n")   # 支持度在这里
  cat(range(t1$edge.length), range(t2$edge.length), "\n")
  ```
- **怎么修**：用 `io_newick_convert` 并显式要求保留支持度、枝长与定根标记；转换后做上面的三项核对。**未定根的树上不能讨论祖先关系**——根的方向一换，所有祖先关系都会反转。

## 4. 统计结果全是显著 / 全不显著

### 4.1 几百个物种全都「显著差异」

- **现象**：差异丰度分析里几乎所有特征都显著，p 值分布极度左偏。
- **可能原因**：四个常见原因叠加。① **没做多重校正**；② **把相对丰度当普通变量做检验**——相对丰度是组成性数据（总和恒为 1），一个特征上升必然伴随其它特征下降，常规检验会产生大量假阳性；③ 样本量太小，每组 n = 3 却做上百次比较；④ 分组与批次完全共线，把技术差异读成了生物学差异。
- **怎么确认**：先看 p 值直方图（是否极度左偏），再看每组样本数，再看分组是否与批次共线（交叉表），最后确认校正方法。
- **怎么修**：组成性数据改用 ANCOM-BC、ALDEx2 等专用方法，或先做 CLR/ILR 变换；对全部检验的 p 值一次性做 `fdr_bh` 校正；样本量不足的组如实标注而不是报 p 值。**不要把「全是显著」当成发现。**

### 4.2 反过来：一个显著结果都没有

- **现象**：p 值直方图接近均匀分布，`padj` 全部不显著。
- **可能原因**：可能是真的没有信号，也可能是流程把信号压掉了：① 校正方法用了控制 FWER 的 `'hs'`；② `topTable` 只取了前 10 行；③ 分组标签错配（样本顺序错位导致组间差异被抹平）；④ 上游定量阶段把差异归一化掉了。
- **怎么确认**：先做无监督检查——PCA/MDS 上样本是否按预期分组聚集？如果分组根本不分离，说明分组变量没有真实效应，p 值不显著是正确结论而非 bug。同时用 `identical()` 确认样本顺序没错配。
- **怎么修**：换 `fdr_bh`；`topTable(number = Inf)`；修正样本顺序；确认归一化方法没有把组间差异消掉。**p 值均匀分布时应如实报告「没有检出差异信号」，而不是继续换方法直到出现显著结果。**

### 4.3 显著性结论与效应量矛盾

- **现象**：`padj` 很小但 fold change 接近 1；或 fold change 很大但完全不显著。
- **可能原因**：① 只报 p 值不报效应量——大样本下极小的差异也能达到 `p < 0.05`，而统计显著不等于生物学重要；② 高表达/高丰度特征的方差估计很稳定，微小变化也能显著；低丰度特征方差大，变化大也不显著。
- **怎么确认**：画 MA 图。低丰度端如果呈「漏斗」状，说明低丰度特征的 log2FC 估计方差很大，其显著结果更可能是噪声。同时把效应量与 p 值一起看。
- **怎么修**：筛选阈值同时考虑两者（如 `padj < 0.05` **且** `|log2FC| > 1`），并在方法里说明理由。只报 `adj.P.Val` 不报 `logFC` 是不完整的。

### 4.4 组成性数据的结论无法解释

- **现象**：某个物种「上升」时，其它所有物种都「下降」；或者结论在不同归一化方法下完全相反。
- **可能原因**：相对丰度总和恒为 1，这是**数学约束而不是生物学现象**。用相对丰度做任何比较时，一个组分的增加在数学上必然压缩其它组分。
- **怎么确认**：检查数据是否已归一化（每列和是否为 1 或 100）；检查使用的检验方法是否为组成性数据设计。
- **怎么修**：用组成性数据专用方法，或做 CLR/ILR 变换后再分析。涉及**绝对数量**变化的结论必须用定量数据（qPCR、spike-in）支撑，不能从相对丰度推断。

### 4.5 PERMANOVA 显著，但各组在图上完全重叠

- **现象**：`adonis2` 的 p < 0.05，但 PCoA 图上各组的点混在一起。
- **可能原因**：**组内离散度不等。** PERMANOVA 检验的是「组间与组内距离的相对大小」；如果某组内部特别分散，它的平均距离更大，即使没有真实的结构差异也会给出显著结果。
- **怎么确认**：做 `betadisper` 并报告结果：
  ```r
  bd <- betadisper(dist_bc, meta$group)
  print(anova(bd))     # 显著 => 组内离散度不等
  ```
- **怎么修**：**PERMANOVA 与 betadisper 必须一起报。** 若离散度不等，应在方法里说明并谨慎解读。另外要明确：PERMANOVA 只说群落整体结构有差异，**不指向任何具体物种**——找差异物种要做差异丰度分析。

### 4.6 聚类「跑出来了」但结果随运行变化

- **现象**：同样的数据，两次运行得到不同的分组。
- **可能原因**：随机初始化没有固定种子。k-means、UMAP、t-SNE、NMDS、稀释（rarefaction）都是随机过程。
- **怎么确认**：连续跑两次，比较分组结果是否一致。
- **怎么修**：所有涉及随机的步骤显式设定种子（`random_state=0` / `set.seed(42)`），并在结果里连同种子一起报告。同时用轮廓系数等指标判断聚类是否可信——**轮廓系数低于 0.25 时基本不可信，应如实报告而不是硬给出分组。**

## 5. 图不可读

### 5.1 缩到期刊单栏宽度后字号看不清

- **现象**：屏幕上看着正常的图，插入论文后标签糊成一团。
- **可能原因**：**按屏幕观感定字号。** 屏幕上 12~14 pt 看着舒服，缩到单栏约 8.3 cm 宽后不可读。这是最常见的退稿原因之一。`ggplot2` 的 `base_size` 默认 11、seaborn 的默认 context 都是为屏幕设计的。
- **怎么确认**：**按最终物理尺寸输出，然后实测**。不要靠想象：
  ```r
  ggsave("fig.pdf", width = 8.3, height = 6, units = "cm")   # 单栏实际尺寸
  ```
  打开这个 PDF，把显示比例设成 100%，看标签能不能读。
- **怎么修**：把字号、尺寸、dpi 固化成样式函数（`viz_pub_style` 的用法），所有图调用它；`base_size` 降到 7~9；`ggsave` 每次显式给 `width`/`height`/`units`。含中文标签时必须用 `cairo_pdf` 并嵌入字体，否则换机器打开会变成方框。

### 5.2 配色在灰度打印或色盲读者眼里无法区分

- **现象**：彩色屏上很清楚，打印成黑白或给色盲读者看时分不清分组。
- **可能原因**：① 用彩虹色盘（`rainbow`/`jet`/`turbo`）表示连续量——它在感知上不等距，会造出并不存在的分界与极值；② 用红绿对比区分分组——约 8% 的男性读者无法区分；③ 分组超过 6~7 个仍只用颜色区分。
- **怎么确认**：把图转成灰度看一眼；用色盲模拟工具过一遍；或者干脆数一下「有几种颜色需要区分」——超过 6 种就该换方案。
- **怎么修**：连续量用 viridis 或单色渐变（`option = "D"` 明度变化更明显，灰度下仍可辨）；分组用蓝橙对比；超过 6 组就**用形状或分面作为第二维度**，或只突出关键分组、其余置灰。

### 5.3 误差线画了，但读者不知道它是什么

- **现象**：柱状图上有误差线，图注里没写是 SD、SEM 还是 95% CI。
- **可能原因**：这三者的宽度差别很大（SEM = SD/√n，95% CI 约等于 1.96×SEM），读者无法反推，也就无法判断组间差异是否可信。
- **怎么确认**：看自己的图注——它有没有说明误差线含义与 n。
- **怎么修**：图注必须写明「误差线为 SD / SEM / 95% CI」以及**每组 n 是多少**。更进一步：**箱线图必须叠加散点**（`geom_jitter` / `sns.stripplot`），因为箱线图会掩盖样本数（n = 3 与 n = 30 看起来一样）与分布形状。

### 5.4 排序图/降维图上读出了不存在的结论

- **现象**：从 PCoA 上「看出」某两组差异大，或从 UMAP 上「看出」两个簇离得很远。
- **可能原因**：① PCoA 不报告轴解释百分比——两轴合计只解释 15% 时，图上的「分离」很可能只是噪声在二维投影上的偶然表现；② NMDS 的 stress > 0.2 仍照常解读；③ 从 **UMAP/t-SNE 上推断簇间距离**——它们只保留局部邻域结构，簇与簇之间的距离、簇的大小都不可定量解释。
- **怎么确认**：看坐标轴标签有没有带百分比；NMDS 图有没有标 stress；每组有几个样本（3~4 个点分开不能当结论）。
- **怎么修**：PCoA 轴标签写成 `PCoA1 (23.4%)` 这种形式；NMDS 必须报 stress（< 0.1 好，< 0.2 可接受，> 0.2 不可用）；要比较组间差异必须回到原始距离矩阵做统计检验（PERMANOVA + betadisper），而不是从图上读。

### 5.5 热图看起来「都差不多」或过度解读

- **现象**：两张热图颜色分布完全一样；或者热图上的块结构被当成结论。
- **可能原因**：① 色标范围随数据自动变化——同一组图必须固定 `breaks`（pheatmap）或 `colorRamp2` 的范围才能互相比较；② **没说明标准化方向**：按行 Z-score 与不标准化画出的图看起来都「像热图」，但回答的问题完全不同；③ 相关矩阵或 Z-score 热图没有让 0 落在色标中点，视觉上把弱相关夸大成强相关。
- **怎么确认**：看色标范围是否一致、是否有 `center = 0` 且 `vmin/vmax` 对称、图注有没有写标准化方向。
- **怎么修**：多张可比的热图固定同一色标范围；`center = 0` 且对称范围；图注写明「按行 Z-score」还是「原始水平」；加列注释色条让图能自我解释。热图的聚类结果**依赖具体距离与连接方法**，作为结论需要做稳健性检查并报告方法。

### 5.6 图上的点数与实际样本数不符

- **现象**：散点图/箱线图上显示的点比实际样本少。
- **可能原因**：① 箱线图的离群点与 `geom_jitter` 把同一个点画了两遍（应设 `outlier.shape = NA` / `showfliers=False`）；② seaborn 在样本很多时会**静默丢弃部分点**（subsampling）；③ `coord_cartesian(ylim=)` 与 `scale_y_continuous(limits=)` 语义不同——后者会**丢弃范围外的数据点**，前者只是放大视野。
- **怎么确认**：数图上的点数并与 `nrow(df)` 对比；检查有没有设 `limits=`。
- **怎么修**：箱线图配散点时关掉离群点绘制；样本量大时显式控制抽样参数；裁剪展示范围时用 `coord_cartesian`，否则统计量会与实际数据不一致。

### 5.7 投稿时被要求提供矢量图，但只有交互式 HTML

- **现象**：用 plotly 做的图无法投稿。
- **可能原因**：**plotly 的定位是探索与网页交付，不是出版。** 期刊要求静态矢量（PDF/SVG）或 ≥ 300 dpi 位图；交互功能在纸上毫无意义。另一个现实原因是浏览器渲染截图的分辨率与字体不可控。
- **怎么确认**：看手上有哪些格式。如果只有 `.html`，就还没有可投稿的图。
- **怎么修**：plotly 用于探索与网页分享，最终图用 `viz_ggplot2` / `viz_seaborn` 重绘。**两者都出不是浪费**——它们解决不同的问题。归档时也要同时保留静态版本，合作方不一定方便用浏览器打开。

## 6. 无法复现

### 6.1 半年后重跑，结果不一样，但所有参数都没改

- **现象**：同一份输入、同一套脚本、同样的参数，结果与当初不同。
- **可能原因**：按可能性排序：① **数据库版本变了**（这是最常见的原因）；② 参考基因组版本变了；③ 工具版本漂移，或依赖库版本漂移；④ 输入数据被替换过而无人察觉；⑤ 存在未固定的随机种子。
- **怎么确认**：逐项核对四件事——软件版本、数据库版本、输入校验和、实际命令。`run_manifest.tsv` 就是为这个场景准备的：
  ```
  tool_kraken2	2.1.3
  ref_db_kraken2	k2_standard_20240605
  input_reads_sha256	3f9a...c21
  ```
  如果这几项里缺了数据库版本，就无法判断——这就是为什么要事先记录。
- **怎么修**：把四项都记进 `run_manifest.tsv` 并随结果归档；数据库用固定发布版本、**不要用 latest**（提供方会在同名文件下更新内容）；输入校验和**每次运行都重新生成**，否则无法区分「同一份数据跑了两次」与「数据换了但没人注意」。

### 6.2 换了电脑/环境就装不上或跑不起来

- **现象**：按文档重建环境时求解失败，或装上了但运行时找不到共享库。
- **可能原因**：① 只留了写死主版本号的 `environment.yml`，没有导出完整依赖树的锁文件；② 通道顺序写错（`defaults` 在 `bioconda` 之前）；③ 用 `pip install` 把包装进 conda 环境，覆盖了 conda 管理的共享库（numpy、htslib、pysam）。
- **怎么确认**：`conda env export` 与手上的 yaml 对比，看依赖树是否完整；`conda list` 里出现 `pypi` 通道的包就是要警惕的信号。
- **怎么修**：导出锁文件（`conda env export --no-builds > envs/x.lock.yaml`，跨平台时加 `--no-builds`）；通道顺序固定为 bioconda → conda-forge → defaults 并开 `strict` 优先级；尽量避免 pip 混装，必须用时在文档里显式记录。

### 6.3 流程「跳过」了本该重跑的步骤

- **现象**：改了参数或换了工具版本，但输出文件没有更新；或者流程报告成功，某个产物却是旧的。
- **可能原因**：① **完整性判据只判断「文件存在」**——被中断的任务留下 0 字节文件，流程以为它已完成；② 引擎按文件时间戳/脚本哈希判断，**不会检测工具或环境的变化**；③ rule/process 的 `output` 声明不完整（实际产出三个文件只声明了一个），引擎认为已完成而跳过。
- **怎么确认**：用引擎的 dry-run 看它打算做什么（`snakemake -n -r`）；对比输出文件的时间戳与实际运行时间；`ls -l` 检查可疑产物的**大小**。
- **怎么修**：判据改成「存在**且非空**」（bash 用 `[ -s "$f" ]`，Python 用 `exists() and stat().st_size > 0`）；改了环境后用 `--forcerun` 显式重跑并在清单里记录重跑范围；`output` 必须列全。Snakemake 侧同时开 `--rerun-incomplete` 清理中断产生的不完整输出。

### 6.4 Nextflow 的 `-resume` 没有生效，全部重跑

- **现象**：加了 `-resume` 却从头开始跑。
- **可能原因**：**`work/` 缓存目录被删了或换了工作目录。** `-resume` 完全依赖这个目录；手工 `rm -rf work` 之后缓存就没有了。另一个原因是 `script` 内容变化导致该 task 的哈希变化——**这是预期行为**，不是 bug。
- **怎么确认**：确认 `work/` 是否存在；对比 `.nextflow.log` 里两次运行的 task hash。
- **怎么修**：清理磁盘时用 `nextflow clean -f -k`（保留最近一次缓存），不要直接删目录；**把 `work/` 与结果目录物理分开**（`work/` vs `results/`），这样清理输出时不会误删缓存。注意 Nextflow 的缓存依据是**声明的输入输出哈希**——进程内使用了未在 `input` 声明的文件时，那些文件的变化不会触发重跑，会得到「看起来成功但用了旧数据」的结果。

### 6.5 容器用了，结果还是对不上

- **现象**：镜像 digest 一致，环境完全相同，结果仍然不同。
- **可能原因**：**容器固定的是软件，不是数据。** 参考数据库、工具索引、分类模型都不在镜像里（体积太大，几十到几百 GB），它们的版本仍需单独管理。这是容器化最容易被忽略的缺口——用了容器之后很容易产生「环境已经固定了」的安全感。
- **怎么确认**：在同一个 digest 的镜像上跑两次，中间替换一次参考数据库。如果结果不同而你没记录数据库版本，就复现了这个问题的全部症状。另外检查镜像引用用的是 `tag` 还是 `digest`——**tag 是可变的**，上游重建同一个 tag 会得到不同内容。
- **怎么修**：把数据库版本管理作为与容器并行的第二条主线：记录库名、版本/日期、来源 URL、提供方公布的校验和。镜像引用一律记 `@sha256:...` digest，**不要在流程里写 `latest`**。用 `util_download_ref` 的写法把四项一起落盘。

### 6.6 只有我一个人能跑这个流程

- **现象**：别人接手时发现少文件、路径写死、或者「在我机器上能跑」。
- **可能原因**：① 依赖了交互式 shell 的初始化（脚本里 `conda activate` 报 `CommandNotFoundError`）；② 依赖当前工作目录（相对路径）；③ 依赖手工设置的环境变量或手工准备的中间文件；④ 参考数据放在个人目录里。
- **怎么确认**：**在一个干净目录、用一份新克隆的代码、按 README 的步骤从头跑一遍。** 这个动作的成本是一小时，收益是知道流程到底能不能被别人用。
- **怎么修**：脚本里显式 `eval "$(conda shell.bash hook)"` 或直接调用环境的绝对路径；用相对于项目根的路径并在开头 `cd` 到项目根；把参考数据放进项目约定目录（`refs/`）并记录版本；把「先手工跑通一步再写进 rule」作为固定习惯。

### 6.7 溯源信息记了，但看不懂

- **现象**：`run_manifest.tsv` 里的字段名过了几个月自己也猜不出含义。
- **可能原因**：清单没有表头与注释行，字段命名不统一，或者版本号只记了主版本。
- **怎么确认**：把文件拿给同事看，问他能不能说出每一项的含义与来源。
- **怎么修**：清单带表头与注释行，说明每个 key 的含义与来源；`--version` 输出有多行时**完整记录**而不是只取第一行数字（`samtools --version` 会连带列出 htslib 版本）；数据库版本与软件版本分开成独立字段。另外，把版本信息记在聊天记录或本地笔记里等于没记——**它必须作为文件与结果一起存放**。

## 7. 结果「看起来正常」但其实是错的

这一节里的错误都不会报错、不改变行数、只改变含义。它们是最危险的一类，唯一的防线是**在每一步入口写一条可执行的校验**。

### 7.1 基因名变成了日期

- **现象**：结果表里的 `SEPT1`、`MARCH1`、`DEC1` 变成了 `9/1/2024` 之类的日期；长数字 id 变成了 `1E+09`。
- **可能原因**：**Excel 在打开文件时自动转换，并在存盘时写回文件。** 这是唯一一个发生在「程序之外」的错误，因此任何校验脚本都看不见。`0012` 会变成 `12`，含逗号的中文会被拆列。
- **怎么确认**：用文本编辑器（而不是 Excel）打开 CSV，搜索 `2024`、`E+`、`/`；或者用程序读回来做类型检查。
- **怎么修**：**权威版本必须是 CSV，xlsx 只作浏览用。** 结果表一律导出 CSV（`to_csv(index=False)` / `write_csv`）；需要给合作者「好看」的文件时另存一份 xlsx，并在文件里写明「此文件仅供浏览，权威版本见 xxx.csv」。如果流程必须产出 xlsx，**同时导出一份 CSV**，不要只留 xlsx。跨 Windows 交付时用 `utf-8-sig` / `write_excel_csv`（带 BOM），否则中文可能乱码。

### 7.2 样本顺序错位，标签整体错配

- **现象**：统计结果合理，但某个样本的数值明显属于另一个样本。
- **可能原因**：按位置对齐的函数（`dist`、`hclust`、limma、DESeq2、`cbind`）遇到顺序不一致的矩阵与元数据。**顺序错了不会报错**，形状完全正常。
- **怎么确认**：进函数前打印两侧标识并断言：
  ```r
  stopifnot(identical(colnames(counts), rownames(meta)))
  ```
- **怎么修**：每次进入按位置对齐的函数前都加断言；能按键对齐就不要用位置对齐。

### 7.3 坐标差 1，翻译出的蛋白起始处不对

- **现象**：取出的 CDS 长度正确但翻译结果不对；或每个基因都错位一个碱基。
- **可能原因**：1-based 闭区间与 0-based 半开区间混用（见 3.5）。另一个原因是**反向链的序列没有做反向互补**——只取坐标不处理链方向，会得到一段看起来合理但完全错误的序列。
- **怎么确认**：取一个已知基因，检查起始密码子是否为 ATG/GTG/TTG，以及有没有内部终止密码子：
  ```python
  protein_full = Seq(fragment).translate()
  print("内部终止密码子:", "*" in str(protein_full)[:-1])
  ```
- **怎么修**：转换代码里写断言；反向链必须 `reverse_complement()` 后再翻译；用 `py_biopython` 或 `io_gff_convert` 的现成写法而不是自己手算坐标。

### 7.4 log2FC 的符号全部反了

- **现象**：上调基因被标成下调，而数值上看不出异常。
- **可能原因**：**对照方向写反。** DESeq2 里 `relevel(ref=)` 设错，或 limma 的 `makeContrasts` 写成 `group_control - group_treat`；也有可能只是因子水平默认按字母序排列，导致参考水平不是你以为的那个。
- **怎么确认**：`levels(dds$group)` 看实际顺序；**抽查一个已知基因的方向**（例如某个已知在处理组上调的基因）。
- **怎么修**：显式设定参考水平（`relevel(dds$group, ref = "control")`）；`makeContrasts` 写成显式表达式后对照实验设计文档核对；结果表里保留对照方向说明。

### 7.5 `padj` 为 `NA` 的行被当成「不显著」删掉

- **现象**：结果表里少了一批特征，方法学部分说不清它们的去向。
- **可能原因**：`NA` 来自**独立过滤**（independent filtering），含义是「该特征的信息量不足以做出可比判断」，与「检验后不显著」不是一回事。
- **怎么确认**：`sum(is.na(res$padj))` 看有多少；看筛选代码里是否用了 `!is.na(padj)` 而没说明。
- **怎么修**：把三类行分开标注（`filtered` / `significant` / `ns`）并在方法里说明；不要静默删除。筛选阈值同时考虑 `padj` 与 `log2FC`，并说明理由。

### 7.6 表里出现了一个名叫 `-` 的分组

- **现象**：分组统计里出现一个 `-` 或 `NA`（作为字符串）的组。
- **可能原因**：工具输出把空字段写成 `-`、`NA`、`N/A`、`none`，而读入时没有把它们声明为缺失值，于是被当成一个真实的类别。
- **怎么确认**：`df["group"].value_counts()` 看有没有奇怪的取值；`unique()` 看全部取值。
- **怎么修**：读取时补上 `na_values=["", "NA", "-", "N/A", "none"]`（Python）或 `na = c("","NA","-","N/A")`（R）；全项目统一缺失值写法，避免「字符串 NA」与「真实缺失」被混为一谈。

### 7.7 差异表达结果在两次分析中不一致，但使用了相同输入

- **现象**：两次跑 DESeq2/limma 的结果有差异。
- **可能原因**：① 低表达过滤阈值不同（大量近零特征会拖累方差估计与多重校正）；② 设计公式不同（有没有协变量）；③ 样本顺序不同；④ 取结果时 `number` 参数不同（limma 默认只返回 10 行）。
- **怎么确认**：把两次运行的设计公式、过滤阈值、样本顺序、`topTable`/`results` 参数都打印出来对比。
- **怎么修**：把过滤阈值与依据写进方法；设计公式写进脚本而不是交互式敲；`topTable(number = Inf)`；样本顺序用 `identical()` 断言。

## 8. 跑得太慢或资源浪费

### 8.1 CPU 大量闲置，但流程很慢

- **现象**：`top`/`htop` 显示只有一个核在跑，其余全是空闲。
- **可能原因**：**工具默认线程数很小。** 最典型的例子是 `fastp`：**默认线程数只有 3**，不显式给 `-w` 就会严重拖慢流程。`FastQC` 默认 `-t 1`，`samtools` 系列默认 1，`Snakemake` 不写 `--cores` 会串行执行。
- **怎么确认**：`top` 看 CPU 占用；看命令行里有没有传线程参数。
- **怎么修**：在每条命令里显式给线程数，并且**与集群申请的 CPU 数对齐**。集群上申请了 32 核却在命令里没传 `-t $SLURM_CPUS_PER_TASK`，是纯粹的浪费——这是最常见的一类资源浪费。

### 8.2 并行跑了一堆任务，整体比串行还慢

- **现象**：同时开 16 个样本、每个 8 线程，总耗时反而更长，机器响应变慢。
- **可能原因**：**并行度超配。** 16 × 8 = 128 线程远超机器核数，大量时间花在上下文切换与内存争抢上。
- **怎么确认**：算一下「样本并行数 × 每样本线程数」与总核数的比值；用 `vmstat`/`pidstat` 看上下文切换频率。
- **怎么修**：唯一正确的算法是 `样本并行数 × 每样本线程数 ≤ 总核数`，并且**写成代码而不是手算**：
  ```bash
  JOBS=$(( $(nproc) / PER_SAMPLE_THREADS )); [ "$JOBS" -lt 1 ] && JOBS=1
  ```
  内存同理：并发数 × 单任务峰值内存不能超过可用内存。

### 8.3 作业排队很久，或者一次占满整个队列

- **现象**：提交一批作业后长时间排队；或管理员抱怨你的作业影响了别人。
- **可能原因**：① 资源申请远超实际需求（内存申请是实际用量的几倍）——白白降低排队优先级；② 作业数组没有限制并发（`--array=1-500` 一次提交 500 个任务）；③ 用 `sleep` 高频轮询作业状态，占满登录节点。
- **怎么确认**：`sacct -j <jobid> --format=JobID,JobName,State,Elapsed,MaxRSS,ReqMem,AllocCPUS` 对比 `MaxRSS` 与 `ReqMem`；`squeue -u $USER` 看并发数。
- **怎么修**：**用实际用量调整下次申请值**（见下一条）；作业数组加 `%M` 限制并发（`--array=1-48%8`）；用 `--dependency=afterok:<jobid>` 串起多步，而不是 `sleep` 轮询（轮询间隔至少 30 秒）。

### 8.4 不知道资源该申请多少，每次凭感觉猜

- **现象**：反复出现「申请太多排队久」或「申请太少被 OOM 杀死」。
- **可能原因**：没有回看实际用量。`sacct` 与 Nextflow 的 `trace` 都能给出每个任务的实际峰值内存与 CPU 利用率，但很多人不看。
- **怎么确认**（这也是修法）：
  ```bash
  # 作业结束后查实际资源用量
  sacct -j <jobid> --format=JobID,JobName,Elapsed,MaxRSS,ReqMem,AllocCPUS,State

  # 按时间段汇总，找出长期超配或 OOM 的作业
  sacct -u "$USER" --starttime today \
    --format=JobID,JobName,State,Elapsed,MaxRSS,AllocCPUS
  ```
- **怎么修**：养成「作业结束后看一眼 `sacct`」的习惯。看两个比值：`MaxRSS / ReqMem` 远小于 1 说明申请过多；`State = OUT_OF_MEMORY` 说明申请不足。优化流程的第一步是看 `trace`，而不是凭感觉调参。实践中经常看到「申请 64 核实际只用 4 核」——这是可以立刻改掉的成本。

### 8.5 单个大文件反复扫描，整体时间被 I/O 吃掉

- **现象**：CPU 占用不高，但流程很慢；`iostat` 显示磁盘忙。
- **可能原因**：同一个大文件被多个步骤反复全量扫描。典型场景：对同一个 BAM 反复做 `samtools depth`、`flagstat`、`view`；或把大表在 Python 与 R 之间反复以 CSV 往返。
- **怎么确认**：看每一步的输入是不是同一个大文件；`time` 一下单独跑一次要多久，乘以步骤数。
- **怎么修**：能一次扫描得出多个统计量的就一次做完；需要按坐标随机访问的先建索引（`io_compress_index`）；跨语言往返用列式格式（`io_interop_standard`）而不是 CSV。但注意：**不要为了性能牺牲可追溯性**——该落盘的中间表还是要落盘，慢几分钟与无法复现不是同一量级的代价。

### 8.6 在错误的粒度上并行

- **现象**：把一个无法并行的小任务拆成 100 份并行，总时间没变；或者把一个可并行的任务串行跑。
- **可能原因**：并行化的收益取决于任务的**粒度与耦合**。把要读同一个几十 GB 索引的任务拆成 100 份并行，每份都要重新加载索引一次，总时间反而变长。反过来，样本间彼此独立的批量任务（每个样本单独跑 fastp）是天然可并行的，串行跑就是浪费。
- **怎么确认**：看并行任务之间是否共享大文件/大索引；测单个任务中「加载」与「计算」各占多少时间。
- **怎么修**：样本间独立的批量任务全力并行；共享大索引的任务考虑合并成一次运行（很多工具支持一次加载处理多个输入）；无法并行的步骤就不要硬拆。判断依据是**瓶颈在加载还是在计算**，不在「能不能拆」。

## 附：排查的通用顺序

遇到问题时，按这个顺序走比随机试参数快得多：

1. **先确认产物是否存在且非空。** `ls -l` 看大小，而不是只看名字。被中断的任务留下的 0 字节文件会产生离真正原因很远的错误信息。
2. **再确认输入是不是你以为的那份。** 看校验和、看文件版本、看来路（哪一步生成的）。很多「参数问题」其实是输入换了。
3. **然后看退出码与日志，而不是看终端最后一行。** `set -o pipefail`；看工具自己的日志文件，而不是被 `tee` 截断的输出。
4. **用最小复现缩小范围。** 取一条记录或一个样本单独跑，能跑通说明是批量/并发问题，跑不通说明是工具或数据问题。
5. **对比一次「上次成功」的运行。** 版本、参数、输入三处逐个 diff。这也是保留 `run_manifest.tsv` 的用处。
6. **改一个变量，跑一次。** 同时改三个参数后结果变好，你仍然不知道是哪个起了作用。
